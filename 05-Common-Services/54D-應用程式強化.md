## 學習目標

- 建立企業應用程式強化的通用基線。
- 能把滲透測試發現轉成具體可驗證的硬化命令與步驟。
- 理解資產清冊、認證、存取控制、更新與備份的優先順序。
- 知道如何用工具驗證強化是否真的生效。

---

## 理論基礎

```text
應用程式強化的本質：把「預設可用」改成「明確允許」

強化優先順序（從最高到最低）：
  1. 資產清冊 → 不知道有什麼，就沒辦法防禦什麼
  2. 管理面存取控制 → 最常被利用的入口
  3. 預設帳號與弱密碼 → 最低成本的突破點
  4. 不必要功能與暴露面 → 減少攻擊面
  5. 版本更新與修補 → 關閉已知漏洞
  6. 監控與告警 → 縮短攻擊者停留時間
  7. 備份與還原 → 勒索軟體與資料破壞的最後防線

常見被忽略的高風險設定：
  - Tomcat /manager/html 對外可達
  - Jenkins 允許匿名存取
  - ColdFusion /CFIDE/administrator/ 無來源限制
  - SNMP community string 仍為 public
  - MSSQL xp_cmdshell 未關閉
  - NFS no_root_squash 設定
```

## 方法一：資產清冊與暴露面盤點

```bash
# 從防禦者角度掃描自己的基礎設施
nmap -sV --open -T4 -oA /tmp/asset_inventory NETWORK_RANGE/24
# --open → 只顯示開放埠（減少雜訊）
# -oA → 同時輸出 nmap / gnmap / xml 三種格式

# 找所有 Web 管理介面（防禦者視角）
nmap -p 8080,8443,8500,8009,4848,9090,9200,5601 NETWORK_RANGE/24 --open
# 8080/8443 → Tomcat / Jenkins / JBoss
# 8500 → ColdFusion
# 4848 → GlassFish
# 9090 → Prometheus / Cockpit
# 9200/5601 → Elasticsearch / Kibana

# httpx 快速識別 HTTP 服務（需安裝）
httpx -l hosts.txt -ports 80,443,8080,8443,8500 -title -tech-detect -status-code
# -title → 頁面標題（快速辨識）
# -tech-detect → 技術棧辨識

# 確認特定服務的管理面是否可達（從外部視角）
for HOST in $(cat web_hosts.txt); do
  CODE=$(curl -s -o /dev/null -w "%{http_code}" --connect-timeout 3 http://$HOST/manager/html)
  if [ "$CODE" == "200" ] || [ "$CODE" == "401" ]; then
    echo "EXPOSED: $HOST → /manager/html → $CODE"
  fi
done
```

## 方法二：Tomcat 強化驗證

```bash
# 確認 /manager 是否限制來源（在 conf/context.xml 或應用 META-INF/context.xml）
cat /opt/tomcat/webapps/manager/META-INF/context.xml
# 應看到類似：
# <Valve className="org.apache.catalina.valves.RemoteAddrValve" allow="127\.0\.0\.1" />
# 若無此設定 → 任何 IP 都能嘗試登入 /manager

# 確認 tomcat-users.xml 是否有管理帳號
cat /opt/tomcat/conf/tomcat-users.xml
# 若有 manager-gui / admin-gui 角色 → 確認密碼強度
# 理想狀態：所有管理角色帳號不存在或密碼極強

# 確認 AJP 是否已停用（防 Ghostcat）
cat /opt/tomcat/conf/server.xml | grep -i "Connector.*8009"
# 若 AJP Connector 未被注解且未加 secretRequired → 存在 Ghostcat 風險
# 安全設定範例：<!-- <Connector protocol="AJP/1.3" ... /> --> （已注解掉）

# 確認 Tomcat 版本（驗證更新狀態）
/opt/tomcat/bin/catalina.sh version | grep "Server version"
# 對照 https://tomcat.apache.org/security.html 確認是否有未修補 CVE
```

## 方法三：常見服務強化驗證命令

```bash
# SNMP — 確認是否仍使用 public community string
onesixtyone -c <(echo "public") TARGET_IP
# 若回傳資訊 → SNMP community string 未更改

# 驗證 SNMP v3 是否啟用（更安全）
snmpwalk -v3 -l authPriv -u USERNAME -a SHA -A AUTHPASS -x AES -X PRIVPASS TARGET_IP .1
# v3 支援加密與認證；v1/v2c 都是明文

# MSSQL — 確認 xp_cmdshell 是否關閉
sqlcmd -S TARGET_IP -U sa -P PASSWORD -Q "EXEC sp_configure 'xp_cmdshell'"
# run_value = 0 → 已關閉（正常）
# run_value = 1 → 開啟！RCE 風險

# MySQL — 確認是否允許匿名登入
mysql -h TARGET_IP -u "" -e "SELECT user, host FROM mysql.user WHERE user='';"
# 若有結果 → 存在匿名帳號（應移除）

# NFS — 確認是否有 no_root_squash
cat /etc/exports
# 若有 no_root_squash → 掛載後 root 不降權 → SUID 攻擊路徑

# SMB — 確認是否允許匿名存取
smbclient -L TARGET_IP -N
# 若列出 share → 匿名可讀（應關閉 null session）

# SSH — 確認是否禁止 root 登入
grep "PermitRootLogin" /etc/ssh/sshd_config
# 應為 PermitRootLogin no
# 確認密碼認證是否關閉
grep "PasswordAuthentication" /etc/ssh/sshd_config
# 應為 PasswordAuthentication no（只允許 key）

# RDP — 確認是否啟用 NLA
# Windows：Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp' -Name UserAuthentication
# UserAuthentication = 1 → NLA 啟用（安全）
# UserAuthentication = 0 → 無 NLA → BlueKeep 等風險
```

## 方法四：認證強化驗證

```bash
# 測試是否存在弱密碼（內部審計）
# 密碼噴灑（單一密碼 vs 多帳號，不鎖定）
crackmapexec smb TARGET_IP -u users.txt -p 'Password123' --continue-on-success
# 若有成功 → 存在弱密碼帳號

# 確認 AD 密碼原則
crackmapexec smb TARGET_IP -u USER -p PASS --pass-pol
# 顯示密碼長度要求、鎖定閾值、複雜度要求

# 確認是否啟用 MFA（WinRM 連線測試）
evil-winrm -i TARGET_IP -u admin -p "ADMIN_PASS"
# 若無 MFA → 密碼即可登入管理介面
# 建議：管理員帳號應強制 MFA

# 檢查預設帳號是否仍存在
# Tomcat
curl -s -u "tomcat:tomcat" http://TARGET_IP:8080/manager/html -o /dev/null -w "%{http_code}"
# 401 → 預設憑證無效（正常）；200 → 預設憑證有效（問題！）

# ColdFusion
curl -s -X POST http://TARGET_IP:8500/CFIDE/administrator/enter.cfm \
  -d "cfadminPassword=admin&requestedURL=%2FCFIDE%2Fadministrator%2Findex.cfm&salt=&submit=Login" \
  -L -o /dev/null -w "%{http_code}"
# 200 → 預設密碼有效（問題！）

# SNMP 預設 community string
onesixtyone TARGET_IP public private community
# 若任一成功 → 更換 community string
```

## 方法五：備份與還原驗證

```bash
# 確認備份檔案是否可被未授權存取（常見錯誤）
# 找公開可存取的備份路徑
for EXT in .bak .backup .old .zip .tar.gz .sql; do
  CODE=$(curl -s -o /dev/null -w "%{http_code}" http://TARGET_IP/backup$EXT)
  echo "backup$EXT → $CODE"
done

# 確認資料庫備份是否可直接下載
curl -s -o /dev/null -w "%{http_code}" http://TARGET_IP/db_backup.sql
# 200 → 嚴重問題！資料庫備份直接暴露

# 確認設定檔是否暴露
for FILE in web.config app.config application.properties .env; do
  CODE=$(curl -s -o /dev/null -w "%{http_code}" http://TARGET_IP/$FILE)
  echo "$FILE → $CODE"
done
# 200 → 設定檔暴露 → 可能含連線字串與密碼

# 驗證備份可還原（防禦者內部驗證）
# 這部分無命令，需流程文件：
# 1. 定期執行還原測試到隔離環境
# 2. 驗證還原後應用可正常運作
# 3. 測試時間（RTO）是否符合 SLA
```

## 決策流程（防禦者優先級）

```
確認資產清冊（nmap -sV --open）
    ↓
管理面是否對外暴露？（curl /manager/html 等）
  → 是：立即限制來源（防火牆 / context.xml Valve）
    ↓
是否存在預設/弱憑證？（crackmapexec 密碼噴灑）
  → 是：立即更改，啟用 MFA
    ↓
是否有未關閉的危險功能？
  → AJP 8009 對外？ → 關閉或限制
  → xp_cmdshell 啟用？ → 關閉
  → NFS no_root_squash？ → 移除
  → SNMP public？ → 更換 community string
    ↓
版本是否過舊？（nmap -sV 確認版本 → 查 CVE）
  → 是：排更新計畫，暫時限制存取
    ↓
監控是否到位？（異常登入 / 掃描偵測）
  → 設定失敗登入告警、異常流量告警
```

grep -E "PermitRootLogin|PasswordAuthentication" /etc/ssh/sshd_config

# 備份暴露確認
for E in .bak .sql .zip; do curl -s -o /dev/null -w "backup$E: %{http_code}\n" http://TARGET_IP/backup$E; done

## 常見錯誤與排查

- 沒有準確資產清冊就談硬化 — 無法防禦你不知道存在的東西。
- 只修 CVE，不處理預設帳號與管理面暴露 — 最危險的往往是最基礎的。
- 有備份但從未驗證還原 — 勒索軟體攻擊時才發現備份無法還原。
- 把 WAF 當成主要防護 — WAF 是最後一層，不是第一層。
- 強化後不驗證 — 應定期用掃描工具從外部視角確認控制是否有效。
