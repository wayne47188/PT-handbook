# 第 11 章 - 子網域列舉

## 標籤

- #cpts
- #chapter

## 學習目標

- 建立 Passive、Active、Brute Force、Permutation 與 Recursive Enumeration 的整合思維。
- 了解字典品質與組織命名規則對列舉成效的影響。
- 掌握 DNS Resolution、Validation 與 Wildcard 排除的必要性。
- 能設計多工具結果合併、去重與優先排序流程。
- 把子網域列舉結果轉成可執行的後續服務驗證清單。

---

## 理論基礎

```text
子網域列舉的本質：找出「能帶出後續攻擊路徑」的高可信度資產

五種方法的分工：
  Passive Enumeration    → 外部資料來源（CT Log / DNS 查詢歷史 / 公開資料集）
                           噪音低、風險小；可能漏掉最新或內部命名
  Brute Force            → 字典暴力猜測，覆蓋率取決於字典品質
  Permutation            → 從已知命名規則衍生（dev-api → staging-api / api-v2）
  Recursive Enumeration  → 從已知子網域衍生更深層命名空間
  DNS Validation         → 用 dnsx 把候選清單過濾為可解析清單

品質控制四層次（必須明確區分）：
  Layer 1：候選名稱（來自各工具原始輸出，含假陽性）
  Layer 2：解析成功名稱（通過 dnsx 驗證）
  Layer 3：非 Wildcard 名稱（排除 Wildcard IP 假陽性）
  Layer 4：非第三方代管（排除 CDN/SaaS CNAME 目標）

高價值優先命名：
  sso / vpn / gitlab / jenkins / jira / api / admin / mail / stage / dev / git
  → 這類名稱比大量品牌子站更值得優先驗證
```

## 多工具整合流程

```bash
# Step 1：被動來源並行蒐集
subfinder -d example.com -silent -o sub_subfinder.txt
# -silent → 只輸出名稱，不含 banner（方便腳本處理）
# -o → 儲存到檔案

assetfinder --subs-only example.com > sub_assetfinder.txt
# --subs-only → 只輸出子網域格式（排除非子網域結果）

amass enum -passive -d example.com -o sub_amass.txt
# -passive → 被動模式（不直接查詢目標 DNS）

curl -s "https://crt.sh/?q=%25.example.com&output=json" \
  | jq -r '.[].name_value' | sed 's/\*\.//g' | sort -u > sub_ct.txt
# 從 CT Log 取得候選名稱（詳見第 10 章）

# Step 2：合併所有被動來源並去重
cat sub_subfinder.txt sub_assetfinder.txt sub_amass.txt sub_ct.txt \
  | sort -u > candidates_passive.txt
# sort -u → 字母排序並去除重複行
wc -l candidates_passive.txt
# 確認被動來源合計候選數量

# Step 3：字典暴力補強（主動方法）
# 用 gobuster 對字典進行暴力解析
gobuster dns -d example.com \
  -w /usr/share/wordlists/seclists/Discovery/DNS/subdomains-top1million-5000.txt \
  -o brute_gobuster.txt -q
# dns → DNS 暴力模式
# -w → 字典路徑（SecLists 推薦）
# -q → 安靜模式（不輸出 banner）

# 萃取成功結果（Found 行）
grep "Found:" brute_gobuster.txt | awk '{print $2}' >> candidates_passive.txt
sort -u candidates_passive.txt -o candidates_passive.txt
# 合併並再次去重
```

## Wildcard 偵測與過濾

```bash
# 先偵測 Wildcard（在大批量驗證前）
dig ns example.com +short
# 取得權威 NS → 例如 ns1.example.com.

WILDCARD_IP=$(dig @ns1.example.com "$(cat /dev/urandom | tr -dc 'a-z' | head -c 12).example.com" +short 2>/dev/null)
# 用隨機字串查詢，取得 Wildcard 的 IP（若有）

if [ -z "$WILDCARD_IP" ]; then
  echo "No wildcard detected"
else
  echo "Wildcard IP: $WILDCARD_IP → will filter from results"
fi

# 批次驗證所有候選
dnsx -l candidates_passive.txt -a -resp -silent -o resolved.txt
# -l → 從檔案讀取候選名稱
# -a → 查 A 記錄
# -resp → 輸出含 IP 的結果（格式：host [IP]）
# -silent → 不輸出 banner

# 過濾 Wildcard 假陽性
if [ -n "$WILDCARD_IP" ]; then
  grep -v "\[${WILDCARD_IP}\]" resolved.txt > resolved_clean.txt
else
  cp resolved.txt resolved_clean.txt
fi
# grep -v → 排除含 Wildcard IP 的行

# 取出主機名稱清單（供後續工具使用）
awk '{print $1}' resolved_clean.txt > hosts_live.txt
wc -l hosts_live.txt
# 最終高品質主機清單
```

## Permutation 擴展

```bash
# 從已知主機名稱歸納命名規則，衍生更多候選
# 例如找到 api-dev.example.com → 嘗試 api-staging / api-prod / api-v2

# 使用 altdns 做 Permutation
altdns -i hosts_live.txt -w /usr/share/wordlists/altdns_words.txt -o permutations.txt
# -i → 已知子網域清單（作為 Permutation 的基礎）
# -w → Permutation 字典（環境標記、版本號、地區碼）
# -o → 輸出候選名稱

# 驗證 Permutation 結果
dnsx -l permutations.txt -a -resp -silent \
  | grep -v "\[${WILDCARD_IP}\]" >> resolved_clean.txt
sort -u resolved_clean.txt -o resolved_clean.txt
```

## 優先排序與後續銜接

```bash
# 高價值命名優先（功能性命名 > 品牌導向命名）
grep -iE "vpn|sso|git|jenkins|jira|api|admin|mail|stage|dev|mgmt|portal" hosts_live.txt \
  > hosts_priority.txt
# -i → 不分大小寫
# -E → 使用擴展正規表示式

# 送入 httpx 驗證 Web 服務
httpx -l hosts_live.txt -silent -status-code -title -o web_alive.txt
# -status-code → 輸出 HTTP 狀態碼
# -title → 輸出頁面標題（快速識別服務類型）

# 送入 naabu 做快速埠掃描
naabu -list hosts_live.txt -top-ports 1000 -silent -o open_ports.txt
# -top-ports 1000 → 掃描最常見的 1000 個埠
```

## 決策流程

```
Seed Domain
    ↓
被動蒐集（Subfinder + Assetfinder + Amass + CT）→ 合併去重
    ↓
Wildcard 偵測（dig @ns 隨機名稱）
  有 Wildcard → 記錄 Wildcard IP
    ↓
批次 DNS 驗證（dnsx -l candidates.txt -a -resp）
  解析失敗 → 丟棄（歷史資料）
  解析成功但 IP = Wildcard IP → 丟棄（假陽性）
  解析成功 → 保留
    ↓
CNAME 追蹤
  指向 CDN/SaaS → 標記供應商，不直接掃描
  指向自有 IP → 進入掃描清單
    ↓
Permutation 擴展（altdns）→ 驗證新候選 → 合併
    ↓
優先排序（高價值命名）→ httpx / naabu / Nmap
```

## 常見錯誤與排查

- 迷信單一工具輸出數量 → 不同工具有不同來源覆蓋，多工具合併才能互補死角。
- 把解析成功直接等同於資產存在 → 仍需排除 Wildcard 假陽性與第三方代管。
- 字典太小或不針對目標 → Permutation 擴展前先分析已知命名規則，針對性擴展效率更高。
- 沒有標記供應商就送進掃描 → 可能掃描到授權範圍外的 CDN 基礎設施。
