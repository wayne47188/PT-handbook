# 第 1 章 - 資訊蒐集總覽

## 標籤

## 學習目標

- 區分 Information Gathering、Reconnaissance 與 Enumeration 在滲透流程中的定位。
- 判斷 Passive、Semi-passive、Active Recon 的風險、證據價值與適用時機。
- 以 Scope、RoE 與資料最小化原則規劃合法且可驗證的偵察流程。
- 從網域、IP、服務、身分與信任關係建立初步攻擊面地圖。
- 評估資料來源的時效、可信度、污染與重複問題，避免錯誤決策。

## 理論基礎

```text
三個層次的定義：

Information Gathering → 最上層總稱，所有授權範圍內的資訊收集
  Reconnaissance → 偵察策略與流程（怎麼找、找什麼、何時停）
    Enumeration → 已知目標上的細部列舉（子網域、埠、使用者、共享）

三種偵察模式與適用時機：

  Passive Recon（被動）：
    完全不接觸目標系統
    來源：WHOIS、CT Logs、搜尋引擎快取、GitHub、求職資訊
    優點：低風險、低可見性
    缺點：資訊可能過時，缺乏即時驗證
    → 每次偵察一定先做這層

  Semi-passive Recon（半被動）：
    對目標周邊做極少量正常互動
    來源：公開 DNS 解析、對 Web 服務送出少量正常請求
    優點：驗證被動資訊，低噪音
    缺點：仍屬接觸目標，需符合 RoE
    → 驗證假說，不是探測

  Active Recon（主動）：
    明確探測目標服務
    來源：埠掃描、服務辨識、目錄列舉、協定互動
    優點：資訊品質最高，即時性最佳
    缺點：可見性高，需完整授權，法律風險上升
    → 確認目標清單後才執行

偵察真正的價值：
  把離散資訊轉成可行決策
  網域 → 子網域 → IP → ASN → 服務 → 技術棧 → 攻擊路徑
  不是「收集越多越好」，而是「每筆資料能支撐哪個決策」
```

## 方法一：被動偵察起手式

```bash
# ── WHOIS / RDAP：找管理線索 ──
whois example.com
# 輸出重點：
#   Registrar → 委託哪家註冊商管理
#   Name Server → DNS 管理權在哪（第三方 or 自有）
#   Creation/Updated Date → 建立時間、最近異動
#   Registrant Organization → 可能是真組織或隱私代理

# ── 基本 DNS 線索（不接觸主機）──
dig ns example.com +short
# +short → 只輸出結果，不顯示 Query/Status 詳細資訊
# 找出權威名稱伺服器（確認 DNS 管理層）

dig mx example.com +short
# mx → Mail Exchange 記錄，找郵件基礎設施
# 判斷郵件是自管（mail.example.com）還是第三方（outlook.com）

dig txt example.com +short
# txt → 常含 SPF、DKIM、驗證 token、第三方整合線索

# ── CT Logs（憑證透明度）：最有效的子網域被動來源 ──
# 線上查詢：https://crt.sh/?q=%.example.com
# 或用 curl
curl -s "https://crt.sh/?q=%.example.com&output=json" | \
  jq -r '.[].name_value' | sort -u
# jq -r '.[].name_value' → 解析 JSON，取出域名欄位
# sort -u → 排序並去重
```

## 方法二：半被動驗證（確認候選資產是否真實）

```bash
# 驗證特定主機是否可解析
dig app.example.com a +short
# a → 只查 A record（IPv4 位址）
# +short → 只回傳 IP，方便快速判斷是否解析成功
# 無回應或 NXDOMAIN → 主機不存在或已停用

# 反向解析（從 IP 找命名線索）
host 203.0.113.10
# 或
dig -x 203.0.113.10 +short
# -x → 反向查詢（自動建構 .in-addr.arpa 查詢）
# 找出 PTR 記錄 → 提示主機用途或命名規則

# 低互動 Web 驗證（確認服務存在，不觸發掃描警報）
curl -I https://app.example.com
# -I → 只取 HTTP 標頭（HEAD 請求），不下載 body
# 看回應碼、Server 標頭、X-Powered-By、Set-Cookie 等指紋線索
# 200/301/302 → 服務存在；503/403 → 可能有 WAF；連線超時 → 可能未開放

curl -s -o /dev/null -w "%{http_code}" https://app.example.com
# -s → silent，不顯示進度
# -o /dev/null → 丟棄 body 輸出
# -w "%{http_code}" → 只輸出 HTTP 狀態碼（快速批量驗證用）
```

## 方法三：資產地圖建立（整合多來源）

```bash
# 從多來源整合子網域清單
# 來源 A：CT Logs
curl -s "https://crt.sh/?q=%.example.com&output=json" | \
  jq -r '.[].name_value' | grep -v '\*' | sort -u > /tmp/subs_ct.txt
# grep -v '\*' → 過濾掉 wildcard 憑證條目（*.example.com 沒有直接價值）

# 來源 B：Subfinder（工具掃描）
subfinder -d example.com -silent -o /tmp/subs_subfinder.txt
# -d → 目標網域
# -silent → 不顯示 banner 與 debug 訊息
# -o → 輸出到檔案

# 合併去重
cat /tmp/subs_ct.txt /tmp/subs_subfinder.txt | sort -u > /tmp/all_subs.txt
wc -l /tmp/all_subs.txt   # 確認合併後總數

# 批量解析驗證（用 dnsx）
dnsx -l /tmp/all_subs.txt -a -resp -silent
# -l → 從清單檔案讀取主機名
# -a → 查詢 A record
# -resp → 顯示解析到的 IP
# -silent → 不顯示 banner
# 只有能解析的主機才進入下一步
```

## 決策流程

```
收到授權目標（網域/IP/組織）
    ↓
Step 1：被動偵察（不接觸目標）
  WHOIS → 管理線索
  CT Logs → 子網域線索
  DNS（公開資料）→ MX/NS/TXT 線索
    ↓
Step 2：整理候選資產（去重、去噪）
  能解析的主機名稱？
    是 → 進入半被動驗證
    否 → 標記為歷史/停用資產，不列入掃描清單
    ↓
Step 3：半被動驗證（最小互動）
  curl -I 確認服務存在？
    有回應 → 標記為活躍資產，列入主動偵察佇列
    無回應 → 可能有 WAF / 防火牆，備註後繼續
    ↓
Step 4：主動偵察（確認清單後才執行）
  埠掃描 → 服務辨識 → 漏洞研究
  （進入後續章節的方法）
```

## 速查表

```bash
# WHOIS
whois example.com

# DNS 線索（被動）
dig ns example.com +short      # 權威 NS
dig mx example.com +short      # 郵件基礎設施
dig txt example.com +short     # SPF/DKIM/第三方

# CT Logs 子網域
curl -s "https://crt.sh/?q=%.example.com&output=json" | \
  jq -r '.[].name_value' | sort -u

# 主機存活確認
dig APP.example.com a +short   # 查 A record
curl -I https://APP.example.com # 確認 Web 服務

# 反向解析
dig -x 203.0.113.10 +short
```

## 常見錯誤與排查

- 把第三方資產（CDN、郵件代管、SaaS 登入頁）誤認成目標自有資產 → 先確認 ASN 歸屬與 TLS 憑證。
- 把 CT Log / 搜尋引擎快取的歷史資料當成現況 → 每筆資產都要做 DNS 解析驗證。
- 忽略 wildcard DNS → 先對隨機不存在主機做對照查詢，確認是否 wildcard 造成假陽性。
- 未記錄來源與時間 → 每筆資產至少記：來源、查詢時間、解析結果、可信度。
- 在未收斂目標前就主動掃描 → 增加噪音，也降低整理品質。
