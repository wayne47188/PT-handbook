# 第 98 章 - 修補建議

## 標籤

- #cpts
- #chapter
- #reporting
- #remediation

## 學習目標

- 理解 remediation 的目標是降低實際風險，而不是只給一般建議。
- 能將建議對應到 finding 的根因、控制點與影響面。
- 知道如何區分立即緩解、長期修復與偵測補強。
- 避免產出與實際環境脫節的模板式建議。
- 讓讀者知道先修什麼、為什麼。

---

## 理論基礎

```text
修補建議的根本問題：

不是「我要告訴讀者應該更安全」
而是「讀者執行這條建議後，這個 finding 的風險是否真正降低」

三層修補結構：

  1. Immediate Mitigation（立即緩解）
     → 現在能做的、不需要大改動的快速降險步驟
     → 範例：移除 sudo 規則、暫時關閉服務、移除多餘帳號
     → 目標：切斷攻擊者立即可利用的路徑

  2. Long-term Remediation（長期修復）
     → 解決根本原因，可能需要架構調整
     → 範例：重新設計 GPO 委派、導入憑證管理、重建 ACL 結構
     → 目標：從設計層面移除弱點，而非打補丁

  3. Detection & Monitoring（偵測補強）
     → 假設攻擊者已在環境中，如何早期發現
     → 範例：啟用稽核日誌、設定 SIEM 規則、監控異常行為
     → 目標：縮短 MTTD（平均偵測時間）

根因映射原則：
  弱點症狀 → 根因控制點 → 修補目標
  不能只治症狀，必須找到「為什麼這個弱點能存在」

好的建議能回答：
  → 要改哪個控制點
  → 為什麼改這裡能降低風險
  → 是否有短期 workaround
  → 是否需要長期架構調整
```

## 根因分析框架

```text
Finding → 根因映射範例：

Finding：www-data 可 sudo 無密碼執行 python3
  症狀：sudo 規則設定不當
  根因：服務帳號缺乏最小權限設計
  控制點：/etc/sudoers / /etc/sudoers.d/
  修補目標：移除規則 + 審查所有服務帳號的 sudo 授權

Finding：Web 應用程式存在 SQLi
  症狀：查詢未參數化
  根因：開發流程缺少安全編碼審查
  控制點：資料庫查詢層（ORM / Prepared Statement）
  修補目標：重構查詢 + 建立 SAST 掃描機制

Finding：IDOR 允許存取他人資料
  症狀：物件存取未驗證身份
  根因：授權邏輯缺失（只驗證認證，未驗證授權）
  控制點：API / 後端業務邏輯層
  修補目標：每次資源存取都驗證請求者是否有權限

Finding：弱密碼重用（憑證噴洒成功）
  症狀：多個帳號使用相同弱密碼
  根因：缺乏密碼複雜度政策 + 未啟用 MFA
  控制點：身份治理（AD 密碼政策、MFA 閘道）
  修補目標：強制密碼複雜度 + 啟用 MFA + HIBP 比對
```

## 修補建議品質對比

```text
# ===== 低品質建議（不可接受）=====

建議：修正權限設定。
建議：更新系統到最新版本。
建議：加強安全性。

問題：
  → 沒有指出具體控制點（改哪裡？）
  → 沒有說明為什麼這樣能降低風險
  → 沒有短期緩解步驟
  → 技術人員無從著手

# ===== 高品質建議（可接受）=====

Finding：root cron 定時執行可寫腳本

Immediate Mitigation（立即緩解，可今日執行）：
  # 步驟 1：移除 world-writable 或 group-writable 位元
  chmod 700 /opt/scripts/backup.sh      # 只有 root 可讀寫執行
  chown root:root /opt/scripts/backup.sh  # 確保 root 擁有

  # 步驟 2：確認 crontab 不再參照可寫路徑
  crontab -l -u root | grep backup.sh
  # 確認腳本路徑正確且無其他可寫依賴

Long-term Remediation（長期修復）：
  # 步驟 3：將所有 root 定時腳本移至受控目錄
  mkdir -p /opt/root-scripts/
  chmod 700 /opt/root-scripts/         # 整個目錄只允許 root 存取
  # 日後新增腳本都放此處，並有 code review 流程

  # 步驟 4：審查 crontab 內的 PATH 設定
  # 危險：PATH=/home/user/bin:/usr/local/bin:/usr/bin
  # 安全：PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin
  # 確保 cron 環境的 PATH 不包含任何使用者可寫目錄

Detection & Monitoring（偵測補強）：
  # 步驟 5：監控關鍵腳本的異動
  # 安裝 auditd 並設定規則：
  auditctl -w /opt/root-scripts/ -p wa -k root_script_modified
  # -w 監控路徑   -p wa 監控寫入與屬性變更  -k 事件標籤
  # 日後可用 ausearch -k root_script_modified 查詢

Affected Scope（影響範疇）：
  所有 root 定時任務所依賴的外部腳本或工具都應檢查，
  不限於本次發現的 backup.sh。

Operational Considerations（營運考量）：
  修改前先確認 backup.sh 的功能，
  避免修改權限後影響現有備份作業。
```

## 常見 Finding 類型的修補框架

```bash
# ===== SQLi =====
# Immediate：啟用 WAF 規則暫時攔截（非根治）
# Long-term：
#   使用 Prepared Statement / Parameterized Query
#   範例（PHP PDO）：
#   $stmt = $pdo->prepare("SELECT * FROM users WHERE id = ?");
#   $stmt->execute([$id]);
# Detection：啟用資料庫查詢日誌，監控異常長度或特殊字元查詢

# ===== XSS =====
# Immediate：對現有輸出加 HTML 編碼（htmlspecialchars()）
# Long-term：
#   Content-Security-Policy Header 限制 script 來源
#   使用框架內建的 XSS 防護機制（React / Angular 預設跳脫）
# Detection：CSP Report-URI 蒐集違規回報

# ===== 提權（sudo 設定）=====
# Immediate：移除問題 sudo 規則
#   visudo -f /etc/sudoers.d/problematic_rule
#   # 直接刪除或限縮權限
# Long-term：
#   導入 PAM 多因素驗證
#   使用 sudoers 的 Command Tag NOEXEC 限制危險二進位
# Detection：/var/log/auth.log 或 journalctl -u sudo 監控

# ===== 憑證重用 / 弱密碼 =====
# Immediate：強制受影響帳號立即重設密碼
# Long-term：
#   AD 密碼政策：最短長度 / 複雜度 / 歷史記錄
#   啟用 MFA（至少對特權帳號）
#   定期使用 HIBP 資料庫比對已外洩密碼
# Detection：設定帳號鎖定閾值 + 異常登入地點告警
```

## 修補優先級排序原則

```text
優先修補的判斷邏輯：

高優先級（本週內）：
  → 可遠端無認證利用的 Critical/High finding
  → 攻擊鏈中的關鍵轉折點（即使單一只是 Medium）
  → 已有公開 PoC 且正在被廣泛利用的 CVE

中優先級（本月內）：
  → 需要認證才能利用的 High finding
  → 影響範圍有限的 Medium finding
  → 需要使用者互動的 finding

低優先級（季度計畫）：
  → Informational / Low finding
  → 需要複雜先決條件才能利用的 finding

特殊處理：
  → 修補成本極高但風險低 → 記錄為已知風險，補強監控
  → 修補會影響業務運作 → 規劃維護窗口，提前測試
```

## 決策流程

```
已驗證 Finding
    ↓
根因分析（症狀 → 根因控制點）
    ↓
撰寫三層修補建議
  Immediate Mitigation（立即可執行）
  Long-term Remediation（解決根因）
  Detection & Monitoring（偵測補強）
    ↓
評估 Affected Scope（影響範疇）
  是否有其他類似設定也受影響？
    ↓
評估 Operational Considerations（營運影響）
  修補步驟是否會影響現有服務？
    ↓
指定優先級（高/中/低）
  依據：風險等級 × 可利用性 × 修補成本
    ↓
完成 Remediation → 納入 Finding 輸出
```

## 速查表

```text
Finding → 根因 → 三層修補：
  Immediate：立即降險（今日可做）
  Long-term：根因修復（需要規劃）
  Detection：偵測補強（假設攻擊者已在內部）

品質自問：
  這條建議執行後，這個 finding 的風險是否真正降低？
  技術人員是否能照步驟執行，而不需要猜測？
  是否說明了「為什麼這樣修能解決問題」？

排除模板式建議的測試：
  → 把這條建議套用到不同 finding 上，
    如果完全通用、不需修改，那就是模板式建議，需要具體化。
```

---

## 常見錯誤與排查

- 套模板式建議（「更新系統」「限制權限」）→ 必須指出具體控制點、具體命令、具體修補對象。
- 只寫治標不寫根因 → 找到「為什麼這個弱點能存在」，從設計層面解決。
- 沒有優先級 → 讀者無法判斷先修哪個，修補效率低落。
- 建議與 finding 不匹配 → 每條建議都應能直接對應 finding 的技術證據與根因。
