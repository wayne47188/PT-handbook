# 第 97 章 - 報告撰寫

## 標籤

- #cpts
- #chapter
- #reporting
- #writing

## 學習目標

- 理解報告的兩類讀者及其不同需求。
- 能將已驗證 finding 轉換為結構完整的報告條目。
- 知道如何區分技術敘述與業務風險語言。
- 避免把掃描器輸出直接貼入報告。
- 讓每個 finding 都能獨立閱讀且自給自足。

---

## 理論基礎

```text
報告的根本問題：

不是「我做了什麼」
而是「不同的讀者需要從這份文件得到什麼」

兩類讀者的根本差異：

  技術讀者（修補者）                決策者（管理者）
  ─────────────────                 ──────────────────
  需要：重現步驟                    需要：業務影響說明
  需要：受影響資產的精確位置        需要：風險排序
  需要：完整的工具輸出              需要：修補成本估計
  不需要：業務語言                  不需要：CVE 編號細節

結構原則：
  Executive Summary → 決策者讀這裡，判斷優先級與資源分配
  Technical Findings → 技術人員讀這裡，照著步驟修補
  Appendix           → 原始工具輸出、截圖目錄、補充資料

每個 Finding 必須能回答五個問題：
  Q1：Where（在哪裡）  → 資產 / IP / URL / 服務
  Q2：Why（為何是問題）→ 這個設定為何不安全
  Q3：How（如何驗證）  → 驗證步驟（可重現）
  Q4：Impact（影響）   → 技術影響 + 業務影響
  Q5：Remediation      → 根因修補 + 緊急緩解

只有能回答上述五個問題的 finding 才達到可報告標準
```

## Finding 撰寫品質對比

```text
# ===== 低品質寫法（不可接受）=====

標題：Sudo 設定問題
描述：系統上有 sudo 設定問題，可能導致提權。
建議：修正 sudo 設定。

問題：
  → 沒有資產位置（哪台主機？）
  → 沒有驗證步驟（如何確認存在？）
  → 沒有具體影響（提權到哪個層級？）
  → 建議空洞（怎麼修正？）

# ===== 高品質寫法（可接受）=====

標題：www-data 帳號可透過 sudo 無密碼執行 python3（高風險）

受影響資產：
  10.10.10.5（Web 伺服器）- Port 80/443

風險摘要：
  Web 服務帳號 www-data 可無需密碼透過 sudo 執行 python3，
  任何能控制 Web Shell 的攻擊者可立即取得 root 權限，
  完全繞過主機身份驗證機制。

技術驗證：
  # Step 1：確認當前身份
  whoami            → www-data
  id                → uid=33(www-data) gid=33(www-data) groups=33(www-data)

  # Step 2：確認 sudo 規則
  sudo -l           → (ALL) NOPASSWD: /usr/bin/python3

  # Step 3：最小化驗證（確認規則成立，不直接執行提權）
  sudo -n python3 -c "print('sudo works')" 2>&1
  # -n → non-interactive，若需要密碼會直接報錯，不卡住等待輸入
  # 輸出："sudo works" → 規則確認成立

技術影響：
  攻擊者可執行 sudo python3 -c "import pty;pty.spawn('/bin/bash')"
  取得 uid=0(root) 的互動 Shell，完全控制主機。

業務影響：
  主機上的所有資料（包含設定檔、金鑰、資料庫連線字串）
  對攻擊者完全開放，且可作為進一步橫向移動的跳板。

修補建議：
  緊急緩解：移除 www-data 的 sudo 規則（/etc/sudoers.d/ 或 /etc/sudoers）
  長期修復：審查所有服務帳號的 sudo 規則，導入最小權限原則
  監控：啟用 sudo 使用稽核日誌（/var/log/auth.log 或 auditd）
```

## Finding 標準輸出格式

```text
Finding 結構模板：

Title：
  [弱點名稱]（[風險等級：Critical/High/Medium/Low/Informational]）

Affected Asset：
  [IP / 主機名稱 / URL / 服務名稱 / 埠號]

Risk Summary（決策者語言）：
  [用 1-3 句話說明這個問題對業務的實際威脅]
  [避免技術術語，著重影響範疇與可能損失]

Technical Evidence（技術讀者語言）：
  [驗證步驟，含完整命令與輸出]
  [引用截圖或附錄編號]

Technical Impact：
  [攻擊者能做什麼，達到什麼技術目的]

Business Impact：
  [技術影響轉換成業務語言：資料外洩、服務中斷、合規問題等]

Remediation：
  Immediate：[緊急緩解步驟，可立即執行]
  Long-term：[根因修復，可能需要架構調整]
  Detection：[監控或稽核補強建議]

References：
  [CVE / 供應商公告 / 設定文件連結]
```

## 風險等級分類標準

```text
風險等級判斷依據（CVSS 輔助 + 環境因素）：

Critical（嚴重）：
  → 可直接取得系統最高權限
  → 無需任何身份驗證
  → 可遠端執行
  → 範例：RCE、預設帳密、未驗證提權

High（高）：
  → 需要低權限才能觸發，或影響範圍較廣
  → 範例：SQLi（有回顯）、IDOR（存取他人資料）、sudo 提權

Medium（中）：
  → 需要特定條件、已驗證攻擊者、或影響有限
  → 範例：反射型 XSS（需使用者點擊）、資訊洩露

Low（低）：
  → 影響極小，難以直接利用
  → 範例：版本資訊洩露、過長的錯誤訊息

Informational（資訊）：
  → 不直接構成風險，但值得注意
  → 範例：HTTP 標頭設定不良、缺少 HSTS
```

## Executive Summary 結構

```text
Executive Summary 應包含（最多 1 頁）：

1. 測試範圍摘要
   → 測試對象、測試期間、測試類型（黑盒/灰盒/白盒）

2. 風險概況
   → 各等級 finding 數量統計（Critical: X / High: X / Medium: X / Low: X）

3. 最高風險路徑（Attack Narrative 摘要）
   → 用 1-2 段說明最危險的攻擊路徑，避免技術細節

4. 優先修補建議（Top 3-5）
   → 依風險×可行性排序，說明修補後的效益

5. 整體安全態勢評估
   → 避免評分制（1-10 分），改用描述性語言
   → 範例：「目前外部攻擊面存在多個高風險入口點，
             內部橫向移動限制不足，建議優先強化身份驗證控制」
```

## 決策流程

```
已驗證 Finding（Verified）
    ↓
填入 Five-Question 模板（Where/Why/How/Impact/Remediation）
    ↓
技術語言 → 技術讀者部分
業務語言 → 決策者 / Executive Summary 部分
    ↓
指定風險等級（Critical/High/Medium/Low）
  依據：嚴重性 × 可利用性 × 環境因素
    ↓
撰寫 Remediation
  緊急緩解（立即可執行）
  長期修復（根因）
  監控補強
    ↓
納入 Attack Narrative（若此 finding 是攻擊鏈的一部分）
    ↓
完成 Finding → 進入 Executive Summary 統計
```

## 速查表

```bash
# Finding 五問快速確認
# Q1 Where：資產 IP / URL / 服務確認
# Q2 Why：為什麼這個設定不安全
# Q3 How：最小化驗證步驟（命令 + 輸出）
# Q4 Impact：技術影響（攻擊者能做什麼）+ 業務影響（對組織的威脅）
# Q5 Remediation：緊急緩解 + 長期修復 + 監控建議

# 風險等級快速判斷
# Critical → 無認證 RCE / 最高權限取得
# High     → 低權限提升 / 廣泛資料存取
# Medium   → 需使用者互動 / 有限資料存取
# Low      → 難以直接利用的資訊洩露
# Info     → 設定建議，不直接構成威脅

# 雙讀者檢查
# Technical section → 技術人員能照步驟重現嗎？
# Executive Summary → 非技術主管能理解業務影響嗎？
```

## 常見錯誤與排查

- 直接貼掃描器輸出當 finding 內容 → 工具輸出是證據，不是 finding 描述，必須轉換成結構化語言。
- 技術語言與業務語言混用在同一段落 → 分開寫：技術讀者段落 vs 決策者段落，各自滿足其需求。
- 修補建議只寫「更新系統」→ 必須指出根因控制點與具體步驟，否則技術人員無從著手。
- Finding 標題不含風險等級 → 標題應包含等級，讓讀者掃描時能立即判斷優先級。
