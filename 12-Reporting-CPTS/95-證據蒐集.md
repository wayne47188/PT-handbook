# 第 95 章 - 證據蒐集

## 標籤

- #cpts
- #chapter
- #reporting
- #evidence

## 學習目標

- 理解證據蒐集在技術可信度與報告品質中的核心地位。
- 能區分觀測結果、工具輸出、作者推論與已驗證事實。
- 知道應保存哪些命令、時間、目標、回應與螢幕截圖。
- 將證據組織成可重現、可追溯、可支撐 finding 的形式。
- 避免只保存零散截圖或只記結論。

---

## 理論基礎

```text
證據蒐集的根本問題：

不是「我拿到了什麼」
而是「任何人看到這份記錄，能否在不依賴我記憶的情況下重建整個 finding」

可追溯性是底線，不是加分項：
  → 你對哪個目標做了什麼（命令 / 請求）
  → 在什麼時間（時間戳）
  → 得到了什麼回應（輸出 / 截圖）
  → 你如何從觀測推到結論（推論說明）

三層認知差異：
  工具輸出  → 機器觀測（你說工具命中了什麼）
  觀測結果  → 可描述的事實（在特定條件下看到了什麼）
  已驗證事實 → 可重現的條件成立（用最小化步驟確認過）

報告中只有「已驗證事實」才能直接當成 finding 結論，
工具輸出和觀測結果需要說明「怎麼從這裡到結論」
```

## 應蒐集的證據類型

```bash
# 類型 1：原始命令（最高可重現性）
# 每條關鍵命令應保存：
#   - 完整命令（含所有選項與參數）
#   - 執行時間（date 命令取得或工具 log 時間戳）
#   - 目標（IP / 主機名稱 / 埠）
#   - 完整輸出（不要截斷）

# 範例：保存 Nmap 命令與輸出
date                               # 先記錄當前時間
nmap -sV -sC -oA evidence/nmap_10.10.10.5 10.10.10.5
# -oA → 同時輸出 .nmap / .xml / .gnmap（見第 23 章）
# 輸出會自動保存到 evidence/ 目錄

# 類型 2：服務互動（Banner / 協定回應）
nc -v target.com 22 2>&1 | tee evidence/ssh_banner_10.10.10.5.txt
# tee → 同時顯示在終端與保存到檔案
# 2>&1 → 把 stderr 也導向 tee（nc 的 banner 通常在 stderr）

# 類型 3：HTTP 請求與回應
curl -v -k https://target.com/admin 2>&1 | tee evidence/http_admin_10.10.10.5.txt
# -v → verbose，顯示完整 request/response headers
# 重要的 Response Body 可加 --max-filesize 限制大小

# 類型 4：漏洞驗證步驟
# 每次最小化驗證都要獨立記錄
# 範例（sudo -l 提權證據）：
whoami                            # 確認當前身份
id                                # 確認 UID/GID/群組
sudo -l                           # 查看可用 sudo 規則
# → 以上三個命令的輸出應一起保存

# 類型 5：截圖補充（UI、系統狀態、關鍵畫面）
# 截圖用於：
#   - Web 應用畫面（難以用文字描述的 UI 狀態）
#   - 系統資訊（登入後的主機名稱 / OS 版本畫面）
#   - 旗標（Flag / 提權成功畫面）
# 截圖命名格式：YYYY-MM-DD_目的_目標.png
# 截圖只用來「補充」原始命令輸出，不能「取代」
```

## 證據目錄結構

```bash
# 建議在測試開始時建立的目錄結構
mkdir -p evidence/{recon,services,web,exploit,privesc,loot,screenshots}
# evidence/          → 根目錄
# recon/             → Nmap、dnsx、httpx 等 Recon 輸出
# services/          → 服務 Banner、協定互動記錄
# web/               → Burp 請求匯出、curl 輸出、Web 截圖
# exploit/           → 漏洞驗證步驟記錄
# privesc/           → 提權過程命令與輸出
# loot/              → 獲取的帳號、Hash、設定檔等
# screenshots/       → 所有截圖（依時間排序命名）

# 每個重要命令用 tee 保存輸出
nmap -sV 10.10.10.5 2>&1 | tee evidence/recon/nmap_10.10.10.5.txt
# 2>&1 → stderr 也一起保存（部分工具輸出在 stderr）

# 保存完整命令歷史（考試或大型測試時）
history | tee evidence/commands_history.txt
# 或持續追加
set -o history
export HISTTIMEFORMAT="%Y-%m-%d %T "   # 加上時間戳
export HISTFILE=evidence/bash_history.txt
export HISTFILESIZE=99999
```

## Finding 的證據對應原則

```text
每個 finding 的證據集應能回答：

問題 1：Where（在哪裡）
  → 資產名稱、IP、埠、URL、服務
  → 範例：10.10.10.5:8080 / http://target.com/login

問題 2：What（觀測到什麼）
  → 原始工具輸出、Banner、HTTP 回應、命令結果
  → 範例：sudo -l 顯示 NOPASSWD: /usr/bin/python3

問題 3：How（如何驗證）
  → 最小化驗證步驟（不需要完整 exploit）
  → 範例：sudo python3 -c "import pty;pty.spawn('/bin/bash')"
  →       得到 root shell，id 確認 uid=0

問題 4：Why（為什麼是問題）
  → 不在證據欄位說明，而是在 finding 描述中解釋
  → 推論部分要明確標示「是作者推論」

Finding 草稿格式（邊測試邊更新）：
  資產：10.10.10.5（Web 主機）
  觀測：sudo -l 輸出顯示 www-data 可 NOPASSWD 執行 python3
  驗證：執行 sudo python3 -c "..." 取得 root shell
  影響：任何可寫 Web Shell 的攻擊者可直接提升到 root
  截圖：screenshots/2024-01-15_privesc_root.png
  狀態：已驗證（verified）
```

## 決策流程

```
發現可疑現象 / 工具命中
    ↓
立即保存原始輸出
  tee 到對應目錄 / 記下時間與目標
    ↓
執行最小化驗證
  每一步驗證都用 tee 保存
    ↓
更新 finding 草稿
  填入：資產 / 觀測 / 驗證步驟 / 影響
    ↓
必要時補截圖
  命名格式：YYYY-MM-DD_目的_目標.png
    ↓
繼續測試，定期整理累積的草稿
  不要等到最後才回頭補記
```

## 速查表

```bash
# 目錄建立
mkdir -p evidence/{recon,services,web,exploit,privesc,loot,screenshots}

# 保存命令輸出
<command> 2>&1 | tee evidence/<category>/<filename>.txt

# 加時間戳
date && <command> 2>&1 | tee -a evidence/commands.log

# 完整 HTTP 記錄
curl -v -k https://target.com 2>&1 | tee evidence/web/curl_target.txt

# 截圖命名規則
# YYYY-MM-DD_目的_目標.png
# 例：2024-01-15_privesc_root_10.10.10.5.png

# Finding 草稿必填欄位
# 資產 / 觀測依據 / 驗證步驟 / 影響 / 截圖 / 狀態（verified/unverified）
```

## 常見錯誤與排查

- 只留截圖不留原始命令 → 截圖不可重現，命令才是最可信的技術記錄。
- 不記錄時間與目標上下文 → 多主機測試時無法回溯「這個輸出對應哪台機器」。
- 把推論混入觀測欄位 → 觀測是事實，推論要明確標示，混在一起會讓 finding 失去可信度。
- 最後才補記證據 → 記憶不可靠，細節會失真，同步記錄是唯一可靠方法。
