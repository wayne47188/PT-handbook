# 第 96 章 - 弱點驗證

## 標籤

- #cpts
- #chapter
- #reporting

## 學習目標

- 理解 finding validation 與單純工具命中的差異。
- 能將掃描器輸出、研究假說與可報告 finding 分開。
- 知道如何設計最小化、可重現、低風險的驗證步驟。
- 將成功與失敗條件都記錄為可辯護證據。
- 避免把可疑現象直接升級成弱點結論。

---

## 理論基礎

```text
Finding validation 的核心問題：

不是「我懷疑有問題」
而是「我能用最小化步驟，讓任何技術讀者都能重現並確認這個問題存在」

三個品質分水嶺：
  工具命中（Tool Hit）    → 工具說可能有問題（未驗證）
  可疑現象（Suspicious）  → 觀測到異常行為（有線索，需驗證）
  已驗證弱點（Validated） → 條件成立，有觀測依據可重現（可報告）

驗證必須回答的三個問題：
  Q1：這個問題是否真的存在？
      （不是工具誤報，不是模板回應，不是 WAF 攔截）
  Q2：在什麼條件下存在？
      （需要哪個版本、設定、帳號、網路位置？）
  Q3：對目標造成什麼實際影響？
      （資料外洩、提權、DoS、橫向移動？）

只有能回答上述三個問題的 finding 才達到可報告標準
```

---

## 最小化驗證設計原則

```text
最小化驗證的設計原則：

原則 1：先讀取，後寫入
  → 先用無破壞性操作確認條件存在
  → SQLi：先用布林判斷，再考慮 UNION 或時間盲注
  → 命令注入：先用 sleep/ping，再考慮反彈 Shell

原則 2：先單步，後組合
  → 一次只驗證一個條件
  → 確認 A 成立 → 再驗證 A+B → 不要一開始就跑完整 PoC

原則 3：記錄失敗條件
  → 「必須在 X 設定下才成立」是有價值的資訊
  → 失敗的對照請求 = 排除誤判的證據

原則 4：對照測試（Baseline）
  → 先送正常請求記錄正常回應
  → 再送測試 payload 觀察差異
  → 差異本身才是證據，不是 payload 本身
```

## 常見弱點類型的驗證方法

```bash
# ===== SQLi 驗證 =====
# Step 1：Baseline（正常請求）
curl -s "https://target.com/item?id=1" > baseline.txt
# Step 2：觸發語法錯誤（布林型）
curl -s "https://target.com/item?id=1'" > test_error.txt
# 若 test_error.txt 含 SQL 錯誤字串（MySQL syntax / ODBC）→ 有 SQLi 線索
grep -iE "sql|syntax|mysql|odbc|ora-" test_error.txt
# Step 3：時間型確認（若無錯誤回顯）
curl -s "https://target.com/item?id=1 AND SLEEP(5)--"
# 若回應明顯延遲 5 秒 → 盲注成立
# Step 4：布林型確認
curl -s "https://target.com/item?id=1 AND 1=1--" > result_true.txt
curl -s "https://target.com/item?id=1 AND 1=2--" > result_false.txt
diff result_true.txt result_false.txt
# 若有差異 → 布林盲注成立（最小化驗證完成，不需要 dump）

# ===== XSS 驗證 =====
# Step 1：基本回顯測試（不帶 <script>，避免 WAF 觸發）
curl -s "https://target.com/search?q=XSSTEST1234" | grep "XSSTEST1234"
# 若輸入值在回應中出現 → 有反射（但還不是 XSS）
# Step 2：確認是否有編碼（HTML 編碼阻止了執行）
curl -s "https://target.com/search?q=<b>test</b>" | grep -c "<b>test</b>"
# 若 <b> 未被編碼（count=1）→ 可能有 XSS
# Step 3：最小 XSS payload（進一步確認）
# 在瀏覽器測試：<img src=x onerror=alert(1)>
# 若 alert 彈出 → XSS 已驗證

# ===== Path Traversal 驗證 =====
# 先嘗試最簡單的穿越
curl -s "https://target.com/file?name=../../../etc/passwd"
# 若回應包含 root: 或 nobody: → 路徑穿越成立
# URL 編碼版（繞過基本過濾）
curl -s "https://target.com/file?name=..%2F..%2F..%2Fetc%2Fpasswd"

# ===== 提權驗證（sudo misconfig）=====
# Step 1：確認當前身份
id
# Step 2：查看 sudo 規則
sudo -l
# Step 3：最小化驗證（若 sudo 允許執行 vim/python/find/less 等）
# 不要直接開 root shell，先確認規則成立
sudo -n python3 -c "print('sudo works')" 2>&1
# -n → non-interactive，若需要密碼會直接失敗（不會卡住等輸入）
# 成功輸出 "sudo works" → 驗證完成，記錄後再決定是否執行提權

# ===== 服務版本驗證（backport 確認）=====
# 看到 Nessus 報告版本型 CVE 後的驗證流程
curl -I https://target.com | grep "Server:"
# 若 Server: Apache/2.4.49 → 記錄此為 Banner 型版本（可信度中）
# 搜尋 Ubuntu/Debian 的 backport：
# https://ubuntu.com/security/notices → 確認是否已修補
```

## 對照測試框架

```bash
# 對照測試的標準流程：

# Step 1：建立 Baseline（正常行為）
curl -s "https://target.com/api/users/1" -o baseline_normal.txt
curl -s "https://target.com/api/users/1" \
  -H "Authorization: Bearer <valid_token>" \
  -o baseline_authenticated.txt

# Step 2：測試目標行為（異常輸入）
curl -s "https://target.com/api/users/99999" -o test_invalid_id.txt
curl -s "https://target.com/api/users/1" \
  -H "Authorization: Bearer <invalid_token>" \
  -o test_invalid_token.txt

# Step 3：比較差異
diff baseline_normal.txt test_invalid_id.txt
# → 若差異只是 "user not found" → 正常行為
# → 若差異是其他用戶資料 → IDOR 成立

# Step 4：記錄結論
# 成功條件：test_invalid_id 回傳了其他用戶的資料
# 前提：不需要認證（或低權限認證）
# 影響：任何用戶可存取任意 user ID 的資料
```

## 決策流程

```
工具命中 / 可疑觀測
    ↓
設計 Baseline（正常請求）→ 保存輸出
    ↓
設計測試 payload（最小化，先讀取後寫入）
    ↓
執行測試 → 保存輸出
    ↓
比較 Baseline 與測試結果
  有差異且可解釋 → 記錄成功條件
  無差異 / WAF 攔截 → 記錄失敗原因，標記為「不確定」
    ↓
記錄失敗條件（同樣重要）
  「必須在 X 設定下才成立」= 有價值的邊界資訊
    ↓
驗證狀態：
  Verified    → 條件成立，有可重現步驟
  Inconclusive → 有線索但無法確認（說明原因）
  Rejected    → 確認不成立（說明排除原因）
    ↓
更新 Finding 草稿（見第 95 章）
```

---

## Finding 驗證狀態標記

```text
Verified（已驗證）：
  → 有明確的最小化驗證步驟
  → 成功觀測可重現
  → 影響可描述
  → 可直接進入報告

Inconclusive（不確定）：
  → 有可疑線索但無法確認
  → 常見原因：WAF 干擾、環境噪音、條件不明
  → 報告時需標明「疑似，待確認」
  → 不要硬寫成 Verified

Rejected（排除）：
  → 確認是誤報（工具 Bug / 版本 backport / 模板回應）
  → 也應記錄排除原因（避免重複測試浪費時間）
```

## 速查表

```bash
# 最小化驗證模板
curl -s "https://target.com/normal" -o baseline.txt    # Baseline
curl -s "https://target.com/test_payload" -o test.txt  # 測試
diff baseline.txt test.txt                             # 比對差異

# SQLi 最小驗證
curl -s "target.com/item?id=1'"          # 觸發錯誤
curl -s "target.com/item?id=1 AND SLEEP(5)--"  # 時間盲注

# XSS 最小驗證
curl -s "target.com/search?q=XSSTEST" | grep XSSTEST   # 確認回顯

# sudo 最小驗證（非互動式）
sudo -n <command> 2>&1                  # -n 避免卡住等待輸入

# 狀態記錄
# Verified / Inconclusive / Rejected + 原因說明
```

## 常見錯誤與排查

- 直接照搬掃描器結果當 finding → 工具命中 ≠ 漏洞成立，必須有最小化驗證步驟。
- 沒有 Baseline 對照 → 沒有正常行為作為參考基準，無法判斷「差異」的意義。
- 只記成功不記失敗條件 → 失敗條件（必須在 X 下才成立）同樣是 finding 的一部分。
- 把 Inconclusive 硬寫成 Verified → 會降低整份報告的可信度，寧可標明不確定。
