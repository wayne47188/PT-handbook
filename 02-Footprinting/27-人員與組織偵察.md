# 第 27 章 - 人員與組織偵察

## 標籤

- #chapter

## 學習目標

- 理解人員與組織情報在技術偵察中的價值。
- 能從職稱、部門、公開簡介與技術描述推回可能的技術棧與攻擊面。
- 分辨高價值的組織線索與低價值背景噪音。
- 了解這類情報如何支援命名規則、技術指紋與社工風險分析。
- 在合法授權與資料最小化前提下使用公開資訊。

---

## 理論基礎

```text
Staff and Organization Recon 的核心問題：

不是「這家公司有哪些人」
而是「從公開組織資訊能推回哪些技術面線索與外部攻擊面」

三個關鍵資訊來源：
  1. 職缺（Job Postings）
       → 招募要求直接揭露技術棧、平台、流程
       → 範例：「熟悉 Azure AD、Okta、SAML、SCIM」→ 身份系統方向
  2. 部門結構與職稱
       → Cloud Team / DevOps / SecOps / Identity / Regional IT
       → 對應的技術負責面：雲端平台 / CI-CD / 安全設備 / SSO / 地區分支
  3. 公開簡介與發表（LinkedIn / 研討會 / GitHub）
       → 供應商關係、使用工具、技術文章、開源專案貢獻

從組織情報到技術假說的轉換才是重點：
  招募提到 Kubernetes + GitLab → 可能有 k8s ingress 子域（registry. / git. / ci.）
  招募提到 Okta / Entra ID → 可能有 SSO 入口（sso. / login. / idp. / auth.）
  招募提到 Palo Alto Prisma → 可能有 VPN/防火牆入口（vpn. / ra. / gp.）
  招募提到 Zscaler → 流量走 Zscaler 雲端 → 真實後端可能難以直接探測
```

## 職缺分析（技術棧推斷）

```bash
# 搜尋目標職缺的策略（不是工具指令，而是查詢設計）

# 搜尋引擎查詢（Google / Bing）：
site:linkedin.com/jobs "example corp" "Azure" OR "AWS" OR "Kubernetes"
# site:    → 限定搜尋來源
# OR       → 找含任一關鍵字的職缺

site:jobs.lever.co "example.com"      # Lever ATS（招募系統）
site:greenhouse.io "example corp"     # Greenhouse ATS
site:boards.greenhouse.io "example"   # 同上，不同路徑
# 這些 ATS 平台常有較完整的技術要求說明

# 搜尋要找的關鍵技術線索：
身份與存取管理：
  Okta / Entra ID（Azure AD）/ Ping Identity / OneLogin / CyberArk
  → 存在 SSO 入口，命名假說：sso.example.com / login.example.com / adfs.example.com

郵件與協作：
  Microsoft 365 / Exchange Online / Google Workspace
  → 搭配 MX / SPF 記錄交叉確認（見第 25 章）
  → Office 365 常有：autodiscover.example.com / outlook.example.com

雲端與基礎設施：
  AWS / Azure / GCP / Terraform / Pulumi
  → 對應雲端資源類型（見第 26 章）

開發與 CI-CD：
  GitHub Enterprise / GitLab / Jenkins / ArgoCD / Tekton
  → 可能子域：git.example.com / gitlab.example.com / ci.example.com / registry.example.com

容器與編排：
  Kubernetes / OpenShift / EKS / AKS / GKE
  → 可能子域：k8s.example.com / api.example.com / dashboard.example.com

VPN 與網路安全：
  Palo Alto GlobalProtect / Cisco AnyConnect / Fortinet / Check Point
  → 可能子域：vpn.example.com / ra.example.com / remote.example.com / ssl.example.com

監控與可觀測性：
  Splunk / Datadog / Grafana / Elastic
  → 可能子域：logs.example.com / monitoring.example.com / grafana.example.com
```

## 部門結構分析

```text
常見部門結構 → 技術面對應關係：

Identity & Access Management (IAM) 部門：
  → 存在企業 SSO、MFA、LDAP/AD 基礎設施
  → 命名假說：sso / adfs / idp / auth / portal / mfa

Cloud Engineering / Platform Engineering：
  → 使用雲端 PaaS 服務、自動化基礎設施
  → 對應雲端子域（依平台）

Network / Infrastructure / Datacenter：
  → 可能有自有 ASN 和自管 IP 網段（見第 25 章 WHOIS）
  → VPN、跳板機、管理介面可能對外暴露

Security Operations (SecOps / SOC)：
  → 使用 SIEM（Splunk/Sentinel）、EDR（CrowdStrike/Defender）
  → 對滲透測試意義：知道對方防禦工具，調整 payload 與行為

Regional IT / Branch Office：
  → 多地區部署 → 可能有地區子域：apac.example.com / eu.example.com / us.example.com
  → 地區 VPN 入口、地區性 AD 域
```

## LinkedIn / 公開簡介分析

```bash
# 搜尋策略（非工具，是查詢設計）

# LinkedIn 搜尋（需登入，或使用 Google 間接搜尋）：
site:linkedin.com "example corp" "Senior Cloud Engineer"
site:linkedin.com "example corp" "Security Engineer" "Splunk" OR "CrowdStrike"

# 從個人簡介提取的線索：
#   技能清單（Skills）: 最直接揭露技術棧
#   過去職稱與專案描述: 有時包含產品或平台名稱
#   推薦文（Recommendations）: 間接提到協作工具或流程
#   發表文章或分享: 技術方向最具體

# GitHub / 技術社群搜尋：
site:github.com "example.com"                # 找目標網域提交
site:github.com "@example.com" "internal"    # 找包含內部網域的程式碼
# 注意：找到的 repo 不一定是現役系統，需要時間戳判斷

# Speakerdeck / SlideShare（研討會投影片）：
site:speakerdeck.com "example corp"
# 投影片常包含架構圖、平台名稱、甚至子網域截圖
```

## 從組織情報到命名假說

```text
情報來源              → 技術假說                  → 待驗證子域列表
--------------------+---------------------------+--------------------------------
職缺：Okta + SAML   → 存在 SSO/IdP 入口         → sso / login / idp / auth / signon
職缺：GitLab + CI   → 存在程式碼托管與 CI 平台   → git / gitlab / ci / registry / pipeline
職缺：GlobalProtect → 存在 Palo Alto VPN 入口   → vpn / gp / ra / remote / ssl
職缺：M365 Exchange → Office 365 郵件環境        → autodiscover / outlook / mail / owa
職缺：Kubernetes    → k8s 管理介面或 API Server  → k8s / api / dashboard / registry
職缺：Grafana/DD    → 監控平台對外暴露           → monitoring / grafana / metrics / logs

→ 這些子域假說應匯入第 11 章子網域列舉的字典（DNS 暴力列舉）
→ 也應在憑證透明度（CT，第 10 章）中驗證是否真實存在
```

## 決策流程

```
收集職缺 / 部門頁面 / 公開簡介
    ↓
提取技術關鍵字
  → 身份系統（Okta/Entra/SAML）
  → 雲端平台（AWS/Azure/GCP）
  → 開發工具（GitLab/Jenkins/ArgoCD）
  → 安全設備（Palo Alto/Fortinet/Zscaler）
    ↓
轉換為技術假說
  每個技術關鍵字 → 對應可能的外部入口類型
    ↓
建立子域候選列表
  加入 DNS 列舉字典 → 驗證（dig / httpx）
  加入 CT 搜尋關鍵字 → 確認（crt.sh / certspotter）
    ↓
交叉比對現有 DNS/HTTP 發現
  若已在 httpx 或 dnsx 結果中出現 → 提升可信度
  若尚未出現 → 保留為「待驗證假說」
    ↓
輸出：技術假說清單（非人員清單）
  欄位：技術線索來源 / 假說方向 / 子域候選 / 驗證狀態
```

## 常見錯誤與排查

- 把單一職缺描述當成完整環境事實 → 職缺是方向，不是確認。技術假說必須經 DNS / HTTP 驗證。
- 收集過多人員細節卻沒有轉成技術假設 → 輸出應是子域候選和技術方向，不是人名電話清單。
- 忽略資訊時效性 → 職缺和簡介可能是 1-2 年前的，優先以 CT 和 DNS 結果為主。
- 沒有回到授權與資料最小化原則 → 不要蒐集個人身份資訊（PII）超出技術偵察所需。
