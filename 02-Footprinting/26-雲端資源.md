## 學習目標

- 理解雲端資源在 reconnaissance 中的典型暴露方式。
- 能辨識雲端前端、物件儲存、負載平衡、託管 DNS 與託管應用的線索。
- 分辨目標自控資源與雲端供應商共享資產。
- 知道如何以低風險方式驗證雲端資源存在性。
- 避免把供應商網域或共享服務直接等同於授權目標。

---

## 理論基礎

```text
Cloud Resource Enumeration 的核心問題：

不是「目標用了哪個雲端平台」
而是「哪些雲端資源真正屬於目標租戶，且對外暴露著什麼攻擊面」

現代目標常見雲端暴露型態：

  1. CNAME 指向物件儲存（S3 / Azure Blob / GCS）
       → 可能有存取控制問題或殘留綁定（dangling CNAME）
  2. CNAME 指向 CDN / 前端加速服務（CloudFront / Azure Front Door / Fastly）
       → 看起來像目標，但流量由供應商處理
  3. CNAME 指向 Web 應用平台（App Service / Cloud Run / Elastic Beanstalk）
       → 屬於目標租戶，有更高滲透價值
  4. A 記錄解析到雲端供應商共享網段
       → IP 在雲端不等於整個網段都是目標

判斷邏輯：
  → 先看 DNS（CNAME 鏈 → 判斷平台）
  → 再看 HTTP/TLS（Header / 憑證 → 確認目標綁定）
  → 最後評估服務類型（儲存 vs 計算 vs 前端 → 決定探測深度）

錯誤判讀後果：
  把 CloudFront 或 Azure Front Door 網段當成目標自有範圍掃描
  → 超出授權、掃到供應商共享基礎設施
```

## CNAME 追蹤與雲端平台識別

```bash
# 步驟一：查 CNAME 記錄（最關鍵的第一步）
dig app.example.com cname +short
# 若輸出含以下關鍵字，判斷對應平台：
#   *.s3.amazonaws.com           → AWS S3 物件儲存
#   *.s3-website*.amazonaws.com  → AWS S3 靜態網站
#   *.cloudfront.net             → AWS CloudFront CDN
#   *.azurewebsites.net          → Azure App Service（目標租戶控制）
#   *.azurefd.net                → Azure Front Door CDN
#   *.blob.core.windows.net      → Azure Blob 儲存
#   *.storage.googleapis.com     → Google Cloud Storage
#   *.run.app                    → Google Cloud Run（目標租戶）
#   *.fastly.net                 → Fastly CDN
#   *.netlify.app / *.vercel.app → 前端應用平台

# 步驟二：追蹤完整 CNAME 鏈（有時是多層轉導）
dig app.example.com +trace
# +trace  → 從根 DNS 一路往下追，顯示每一層委派
# 用途：看清楚 CNAME 多層包裝，例如 app.example.com
#         → lb.example.com → d1abc.cloudfront.net → 最終 IP

# 步驟三：查最終解析 IP（確認是否落在雲端網段）
dig app.example.com a +short
# 搭配 whois 確認 IP 歸屬（見第 25 章 WHOIS）
# 注意：IP 落在 AWS/Azure/GCP 網段，不代表整個網段都是目標
```

## HTTP Header 分析（識別前端服務）

```bash
# 基本 Header 抓取
curl -I -k https://app.example.com
# -I       → 只抓 HTTP Header（不下載 body）
# -k       → 跳過 TLS 憑證驗證（自簽憑證或錯誤 CN 時用）

# 判斷前端類型的關鍵 Header：

# AWS CloudFront：
#   X-Cache: Hit from cloudfront
#   Via: 1.1 abc123.cloudfront.net (CloudFront)
#   X-Amz-Cf-Id: 

# Azure Front Door / Azure CDN：
#   X-Azure-Ref: 
#   Server: AzureDirect / Microsoft-Azure-Application-Gateway

# Akamai：
#   Server: AkamaiGHost
#   X-Check-Cacheable: YES

# Fastly：
#   X-Served-By: cache-*.fastly.net
#   X-Cache: HIT

# Cloudflare（見第 25 章）：
#   Server: cloudflare
#   CF-RAY: 

# S3 靜態網站（沒有 CDN 包裝時）：
#   Server: AmazonS3
#   x-amz-request-id: 
#   x-amz-id-2: 

# 若 Header 顯示「後端是 CDN 前端」 → 標記為前端，不掃供應商網段
# 若 Header 顯示應用框架（nginx / Apache / IIS）→ 可能是目標自管或租戶計算資源
```

## TLS 憑證分析（確認租戶綁定）

```bash
# 用 openssl 查看 TLS 憑證細節
echo | openssl s_client -connect app.example.com:443 2>/dev/null | \
  openssl x509 -noout -subject -issuer -dates
# -connect → 建立 TLS 連線
# x509    → 解析憑證格式
# -noout  → 不輸出憑證原始 PEM，只看解析後資訊
# -subject → CN（Common Name）= 憑證綁定的網域
# -issuer  → 憑證簽發者（CA）
# -dates   → 有效期（notBefore / notAfter）

# 判斷邏輯：
#   issuer: Cloudflare / DigiCert-CloudFlare  → CDN 代理憑證
#   issuer: Amazon / DigiCert                 → 可能 ACM（AWS Certificate Manager）→ 租戶控制
#   issuer: Let's Encrypt                     → 常見自動申請，目標自管或 PaaS
#   CN = *.example.com（SAN 含目標網域）      → 目標有主動綁定此域名

# 查看 SAN（Subject Alternative Names，更完整的網域清單）
echo | openssl s_client -connect app.example.com:443 2>/dev/null | \
  openssl x509 -noout -text | grep -A1 "Subject Alternative Name"
# SAN 中出現的其他網域名稱 → 子域線索（間接發現資產）
```

## httpx 批次掃描（快速 Profiling）

```bash
# 對多個主機做批次 HTTP Profiling
httpx -l hosts.txt \
  -sc \            # 顯示 HTTP 狀態碼
  -title \         # 抓頁面 <title>
  -server \        # 顯示 Server Header
  -tech-detect \   # 技術指紋識別（Wappalyzer 規則）
  -silent \        # 不輸出 banner，只輸出結果
  -o httpx_cloud.txt
# 輸出範例：
# https://portal.example.com [200] [Portal Login] [nginx] [AWS CloudFront,React]
# https://files.example.com  [403] []             [AmazonS3]

# 判斷邏輯：
#   tech-detect 出現 CDN 供應商 → 前端，不直接掃供應商網段
#   tech-detect 出現應用框架   → 目標租戶計算資源，優先深入
#   狀態 403 + AmazonS3       → S3 bucket 存在但無列表權限，嘗試存取具體 key
#   狀態 200 + 無 CDN 指紋    → 可能是目標直接提供服務
```

## 殘留綁定（Dangling CNAME）偵測

```bash
# 什麼是 Dangling CNAME：
# 某個 DNS CNAME 仍指向雲端服務，但目標已經關閉了那個租戶資源
# 攻擊者可以在供應商上重新建立同名資源，劫持流量

# 偵測方法：
dig old.example.com cname +short
# 若輸出 xyz.azurewebsites.net 或 xyz.s3-website.amazonaws.com 等
curl -I https://old.example.com
# 若回應 404 / NoSuchBucket / No such app → 疑似 Dangling CNAME

# 驗證是否為 Dangling：
# 條件1：CNAME 仍存在（dig 有結果）
# 條件2：後端資源不存在（curl 回 NoSuchBucket / ResourceNotFound）
# 條件3：目標網域沒有其他 CNAME 或 A 指向同一服務

# 回報時注意：Dangling CNAME 屬於授權範圍內的配置問題，不要實際劫持
```

## 資產類型與風險對照

```text
服務類型                | CNAME 特徵                    | 風險方向
------------------------+-------------------------------+-----------------------
物件儲存（S3/Blob/GCS） | *.s3.amazonaws.com 等         | 存取控制、公開列表、Dangling CNAME
靜態網站（S3 hosting）  | *.s3-website*.amazonaws.com   | 內容注入（若可寫）
CDN 前端               | *.cloudfront.net / *.azurefd  | 繞過限制、Header 注入（通常低）
PaaS 應用              | *.azurewebsites.net / *.run.app | 應用層漏洞（目標租戶直接控制）
API Gateway            | *.execute-api.*.amazonaws.com | API 端點探測、認證測試
```

## 決策流程

```
已知子域名 / 主機名稱
    ↓
dig CNAME +short
  有 CNAME → 判斷指向哪個雲端平台
  無 CNAME → dig A +short → whois IP → 判斷 ASN 歸屬（見第 25 章）
    ↓
CNAME 指向物件儲存（S3/Blob/GCS）？
  是 → curl 驗證是否公開存取 / 是否 Dangling → 記錄存取控制狀態
  否 → 繼續下一步
    ↓
CNAME 指向 CDN/WAF 前端（CloudFront/Front Door/Fastly）？
  是 → 標記為「CDN 前端，不掃供應商網段」→ 嘗試找真實 Origin IP
  否 → 繼續下一步
    ↓
CNAME 指向 PaaS/計算資源（azurewebsites/run.app/elasticbeanstalk）？
  是 → 確認租戶歸屬（TLS 憑證 CN / 頁面內容）→ 標記為「目標租戶，優先探測」
    ↓
HTTP Header 分析
  curl -I 確認前端特徵 / Server Header / Cache Header
    ↓
TLS 憑證分析
  確認 CN 與 SAN → 提取額外子域線索
    ↓
更新資產地圖（欄位：名稱/CNAME指向/平台類型/租戶綁定/探測優先級）
```

## 速查表

```bash
# CNAME 追蹤
dig <subdomain> cname +short          # 查 CNAME 指向
dig <subdomain> +trace                # 完整委派鏈追蹤
dig <subdomain> a +short              # 最終解析 IP

# HTTP 分析
curl -I -k https://<target>           # Header 識別前端類型

# TLS 憑證
echo | openssl s_client -connect <target>:443 2>/dev/null | \
  openssl x509 -noout -subject -issuer -dates

# 批次掃描
httpx -l hosts.txt -sc -title -server -tech-detect -silent -o httpx_cloud.txt
```

## 常見錯誤與排查

- 把 CloudFront / Azure Front Door IP 當成目標自有網段掃描 → 先確認 CNAME，再判斷是否為共享 CDN。
- 看到雲端指紋就直接結論「找到目標」→ 還需確認是否為目標租戶綁定（TLS CN / 頁面內容驗證）。
- 忽略 Dangling CNAME → CNAME 存在但後端資源已消失，應記錄為配置問題。
- 對共享 PaaS 平台大範圍掃描 → 即使是目標租戶的 PaaS 資源，也只探測目標網域，不掃整個 azurewebsites.net。
